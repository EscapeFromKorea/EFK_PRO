# 1. 경량 도형 블록 들어올리기 (Block Carry)

`Assets/BlockCarrySystem/` · 이슈 #83 · 커밋 `f55c500`(신설) + `74ec65b`, `b3732c1`(QA 수정)

## 무엇인가

구·정사면체가 딱딱 블록(`SnapBlock`) 1개를 머리 위에 얹어 들고 이동·점프해, 턱이나 선반 위에 올려놓는다. 정육면체는 거부된다(무게는 도킹 담당).

## 조작

- 블록 3.5유닛 안으로 다가가면 조준점(구)이 뜬다 — 하양=들 수 있음, 빨강=거부(도형/질량/결합구조물)
- **`C`**: 픽업 / 내려놓기 토글. 내려놓기는 전방·상단이 비어 있을 때만 허용(막히면 빨강+거부)

## 동작 원리

| 파일 | 역할 |
|---|---|
| `PlayerBlockCarrier.cs` | 근접 타겟팅·픽업/드롭·자동 드롭 감시. 플레이어에 런타임 `AddComponent`. |
| `BlockCarryController.cs` | 씬 진입점, 튜닝값 배포. |

**점프 높이 불변의 원리**: 든 블록의 `Rigidbody.isKinematic = true`로 전환해 플레이어 `Rigidbody` 질량에 0 기여. `PlayerJump.LaunchToHeight`가 질량 무관 `velocity = √(2gH)` 대입이라, 도형 스탯 점프 높이가 빈손과 동일하게 유지된다.

**회전 고정의 원리**: 부모화나 조인트 대신, `LateUpdate`에서 블록 위치만 `player.position + up*carryHeight`로 직접 갱신하고 회전은 픽업 순간 값에 고정. 구가 실제 물리로 굴러도 블록은 안 돈다.

**자동 드롭**: 리스폰·리셋(순간이동 감지) / 크기 변형(`localScale` 변화 감지) / 굴리기 모드(`PlayerRollModeReceiver` 존재) / 실타래 매달림(`ExternallyDriven`) 진입 시 현재 위치에 즉시 드롭 — 소프트락 방지.

## QA에서 찾아 고친 것

### 굴러갈 때 "꿀렁꿀렁"하며 도는 것처럼 보임 (실측·플레이테스트로 확인)

**증상**: 구를 조작해 움직이기만 해도(블록을 들지 않아도) 재현. 원인 두 개가 겹쳐 있었다.

1. **든 블록의 `Rigidbody.interpolation`이 `Interpolate`로 켜져 있었음** — 매 프레임 `transform`을 직접 갱신하는 방식과 충돌해 물리 스텝마다 위치가 살짝 튀었다 복구되는 것처럼 보임. → 든 동안은 `RigidbodyInterpolation.None`으로(`74ec65b`).
2. **(진짜 원인) `UpdateTarget()`이 매 Update 프레임 `FindObjectsOfType<SnapBlock>()`으로 씬 전체를 훑었음** — 매번 새 배열을 GC 할당해 주기적 GC 히치가 발생, 실제 물리로 구르는 도형이라 그대로 눈에 보이는 흔들림이 됨. 블록을 안 들어도 재현되는 것과 정확히 일치. → 대상 재탐색을 **0.15초 간격**으로 제한(`b3732c1`).

```csharp
// Assets/BlockCarrySystem/PlayerBlockCarrier.cs (수정 후 핵심)
if (carried == null && Time.time >= nextRetargetTime)
{
    UpdateTarget();
    nextRetargetTime = Time.time + Mathf.Max(0.02f, retargetInterval);
}
```

**해결책 A** — 재탐색 간격 제한 (채택, 적용됨): 응답성 체감 차이 없이 GC 압력을 ~85% 감소.
**해결책 B** — `NonAlloc` 오버랩 API로 교체 (기각): 근본적으로 더 낫지만 이번 QA 범위를 넘는 리팩터라 후속 과제로 미룸.

(참고: 나머지 기존 기믹들 — `SnapBlockController`, `FrictionStickerSystem/PlayerStickerCarrier` — 도 같은 패턴으로 매 프레임 `FindObjectsOfType`을 쓴다. 이번엔 내 신규 코드만 고쳤고, 기존 파일은 무수정 원칙상 손대지 않았다 — 필요하면 별도 이슈로 제안할 것.)

## 플레이테스트 결과 (mnppi 실측)

정사면체·구 픽업/점프/이동/드롭/거부/자동드롭 전부 정상. 굴러갈 때 흔들림 완전히 사라짐 확인.

# 2. 정육면체 블록 도킹 (Cube Dock)

`Assets/CubeDockSystem/` · 이슈 #84 · 커밋 `6d76500`(신설) + `b3732c1`, `a0c9ad9`, `4966bb7`(QA 수정)

## 무엇인가

정육면체가 딱딱 블록(또는 여러 블록이 결합된 구조물)에 자기 몸을 결합해, 그 구조물을 끌고 다니거나 절벽 가장자리에서 결합을 유지한 채 남아 다른 도형이 건너는 다리의 고정 앵커가 된다.

## 조작

- **`H`**(원래 `G`였으나 아래 사유로 변경): 도킹 / 해제 토글
- 정육면체 박스 6면 ↔ 블록 6면의 거리·각도 근접 판정(딱딱 블록 결합과 동일 기준)

## 동작 원리

| 파일 | 역할 |
|---|---|
| `PlayerCubeDock.cs` | 근접 타겟팅·면쌍 후보 탐색·전용 `ConfigurableJoint` 결합/해제. |
| `CubeDockController.cs` | 씬 진입점, 튜닝값 배포. |

정육면체 Rigidbody에 `connectedBody = 대상 블록`인 전용 `ConfigurableJoint`를 붙인다(`SnapBlock.Weld`와 별도 관리 — 프록시 SnapBlock을 안 만드는 이유는 `SnapBlockController`가 오인하기 때문). `IsControlled == false`(Tab으로 조작을 넘김)에도 조인트를 파괴하지 않아 정육면체가 앵커로 남는다.

## QA에서 찾아 고친 것

### ① 도킹하자마자 조작 없이 위치가 끌려감 (실측·플레이테스트로 확인, 심각도 상)

**증상**: 특히 블록 여러 개가 결합된 구조물에 도킹하면 두드러짐.

```csharp
// Assets/CubeDockSystem/PlayerCubeDock.cs — 수정 전
joint.angularXMotion = joint.angularYMotion = joint.angularZMotion = ConfigurableJointMotion.Locked;
joint.projectionMode = JointProjectionMode.PositionAndRotation;
joint.projectionAngle = 1f;
```
```csharp
// 수정 후
joint.angularXMotion = joint.angularYMotion = joint.angularZMotion = ConfigurableJointMotion.Free;
joint.projectionMode = JointProjectionMode.PositionAndRotation;
// projectionAngle 제거 — 각 구속이 없어 무의미
```

**원인**: 정육면체 Rigidbody는 이미 `RigidbodyConstraints.FreezeRotation`으로 월드 기준 회전이 잠겨 있는데, 조인트에 `angularMotion = Locked`까지 걸어 "블록 기준 상대 회전 고정"을 동시에 요구했다. 서로 다른 두 기준(월드 vs 블록 상대)의 회전 구속이 물리 솔버가 못 푸는 각 오차로 남았고, 그 오차가 선형(위치) 쪽으로 새어나와 조작 없이 끌려다니는 것처럼 보였다. 여러 블록이 결합된 구조물은 자체 `SnapBlock.Weld` 조인트 체인 때문에 절대 회전 기준이 더 안 잡혀 있어 특히 심했다.

**해결책 A** — 각축 Free, 회전은 `RigidbodyConstraints`에 위임 (채택, 적용됨): 이 저장소에 이미 선례가 있었다 — `DreamThreadController`가 플레이어에 조인트를 걸 때 정확히 같은 이유로 이미 이 패턴을 쓰고 있었다.
**해결책 B** — 각축 Locked 유지하고 `breakTorque`를 낮춰 억지로 풀리게 (기각): 폭주의 증상만 완화할 뿐 원인(이중 구속)은 그대로 남는다.

### ② `Position` 단독 `JointProjectionMode` 값 사용 — 컴파일 에러 (①의 수정 과정에서 발생)

Unity API에 `JointProjectionMode.Position`은 없다(`None` / `PositionAndRotation` 둘뿐). ①을 고치며 실수로 존재하지 않는 값을 써서 `CS0117` 컴파일 에러가 났다 — mnppi가 Console에서 직접 발견해 리포트. `PositionAndRotation`으로 정정(같은 커밋 `a0c9ad9`에 amend로 합침).

### ③ 도킹 키 `G`가 `ThreadPinPlacer`(꿈의 실타래 세모 실핀)와 충돌

관성 축전기 데모 리그를 만들며 전체 키 배정을 다시 훑다 발견. `F`/`G`/`T`가 이미 실타래 쪽에 쓰이고 있었는데 도킹 키를 `G`로 겹쳐 잡았었다. `H`로 변경(`4966bb7`).

## 플레이테스트 결과 (mnppi 실측)

도킹/해제/끌기/다리 앵커/도형 전환 유지/자동 해제/구·정사면체 거부/기존 `E` 결합 회귀 없음 — 전부 정상 확인. 수정 전엔 "조작도 안 했는데 어디론가 끌려간다"를 직접 재현해 리포트.

# 3. 관성 축전기 (Inertia Capacitor)

`Assets/InertiaCapacitorSystem/` · 이슈 #85 · 커밋 `1a96e04`(신설) + `a5f6660`, `8c7130b`, `43f050c`(QA 편의)

## 무엇인가

충돌 운동량(질량 × 상대속도)을 저장했다가 스스로 풀어내며 연결 장치를 구동하는 축적기. 태엽 축(`WindupAxle`)과 같은 "충전-방전" 구조지만 입력이 손잡이 회전이 아니라 **충돌**이다.

## 동작 원리

| 파일 | 역할 |
|---|---|
| `InertiaCapacitor.cs` | 충전(`OnCollisionEnter` → `Collision.impulse`) / 방전(연속+버스트) / 출력 본체. |
| `Editor/InertiaCapacitorMenuItem.cs` | 씬 세팅 메뉴 + 데모 리그. |

**핵심 설계 결정 — 수신자 계약을 기존 `IWindupReceiver` 재사용**: 태엽 축용으로 만든 레일카·회전판 등 출력 장치가 **코드 수정 없이** 그대로 배선된다. `InertiaCapacitorSystem`은 `WindupAxleSystem`의 public 인터페이스를 읽기만 해서 교차 폴더 규약을 안 어긴다.

- 같은 물체가 계속 닿아 있어도 `OnCollisionEnter` 1회 + 쿨타임으로만 충전 → 중복 누적 없음
- `charge`는 항상 `0~maxCharge` 클램프 → 완충 상태 추가 충돌 폭주 없음
- `maxChargePerHit`(0=무제한)로 포탈 고속 물체는 대량 충전하되 글리치성 단발만 선택적으로 클램프 가능

## QA 편의로 추가한 것 (로직 변경 없음)

- **콘솔 로그 추가**(`a5f6660`): 원래 발광 연출과 UnityEvent(기본 비어있음)뿐이라 충전이 실제로 되는지 눈으로만 판단해야 했다. `[InertiaCapacitor]` 접두사로 충전/완충/완전방전/버스트 시점을 로그로 — 나머지 기믹과 동일하게 Console만 보고 QA 가능하게 맞춤.
- **원클릭 데모 리그**(`8c7130b`): `Tools > InertiaCapacitorSystem > Create Demo Rig` — 캡시터 + `WindupAxleSystem`의 회전판을 나란히 놓고 `Output Targets` 배선까지 끝낸 상태로 생성. "실제 장치를 구동하는지" Inspector 드래그 없이 바로 테스트 가능.
- **회전판 스텝 90도로**(`43f050c`): 원본 기본값(15도)은 시연에서 눈에 잘 안 띄어서, 데모 리그 생성 코드에서만 90도로 지정(원본 `RotatingPlatform` 기본값은 무수정).

## 플레이테스트 결과 (mnppi 실측)

충전(강한 충돌 vs 무시되는 약한 접촉)/중복 방지/방전/완충 클램프/완전방전 5개 항목 전부 정상. 데모 리그로 버스트→회전판 구동까지 확인 — 회전판이 15도씩 ~3초 지연 후 도는 건 회전판 자체의 기존 설계(연속 출력 무시, 버스트 전용)라는 점도 확인.

# 4. 동기화 오브젝트 (Sync Object)

`Assets/SyncObjectSystem/` · 이슈 #86 · 커밋 `88ffeba`(신설) + `1a5e1d1`, `7f6e704`, `c00b601`, `c3b0135`(QA 수정)

## 무엇인가

같은 `pairId` + 같은 도형을 가진 두 오브젝트가 짝을 맺어, 한쪽(Leader)의 움직임을 다른 쪽(Follower)이 미러한다. 유리벽·다른 방으로 분리된 공간의 플랫폼·엘리베이터·무게 발판을 원격 조작하는 용도.

## 동작 원리

| 파일 | 역할 |
|---|---|
| `SyncObject.cs` | 페어링·모드(위치공유/반전/회전/무게반응)·축별 토글·범위 클램프. |
| `SyncDemoGravityToggle.cs` | 데모 전용 — Leader 중력을 키(`Z`)로 토글. |
| `Editor/SyncObjectMenuItem.cs` | `Create Sync Pair` 메뉴. |

**오차 누적 방지의 원리**: 타깃을 항상 "초기 위치 + 오프셋" **절대값**으로 계산(델타 누적 안 함). Follower는 `isKinematic`이라 플레이어가 못 밀어 독립 입력이 없다 — 에코(피드백 루프) 자체가 안 생긴다.

## QA에서 찾아 고친 것 (전부 데모 리그 설정 — `SyncObject.cs` 본체 로직 무변경)

### ① 밀면 마찰 없이 영원히 미끄러짐 → "무중력처럼 떠다닌다" (실측·플레이테스트로 확인)

데모 큐브에 `useGravity=false`만 넣고 `drag`를 0으로 뒀던 게 원인 — 한 번 밀리면 안 멈추고 계속 미끄러짐. Leader에 `drag`/`angularDrag` 3 추가(`7f6e704`).

### ② 중력 설정이 명세서 요구사항인지 확인 필요 → 명세서엔 없는 임의 설정이었음

노션 요구사항 원문 재확인 결과 중력/물리 낙하 관련 요구는 전혀 없었다. 테스트 편의로 넣은 임의 선택이었다는 걸 확인(mnppi 질문으로 재점검).

```csharp
// Assets/SyncObjectSystem/Editor/SyncObjectMenuItem.cs — 최종
rb.useGravity = false;          // 기본은 꺼짐 — 어디 둬도 그 자리에 그대로 있어 정밀 배치 쉬움
rb.isKinematic = role == SyncObject.SyncRole.Follower;
if (role == SyncObject.SyncRole.Leader)
{
    rb.drag = 3f;
    rb.angularDrag = 3f;
    go.AddComponent<SyncDemoGravityToggle>();   // Z키로만 중력 활성화
}
```

**해결책 A** — 항상 중력 켜기 (중간 단계에서 적용했다가 기각): 허공에 스폰하면 바로 떨어져버려 배치가 번거로움.
**해결책 B** — 기본 꺼짐 + 키 토글로 필요할 때만 활성화 (채택, 최종 적용 `c3b0135`): "버튼 눌러야 활성화" 요청에 맞춰, 평소엔 정밀 배치가 쉽고 낙하 거동은 원할 때만 `Z`로 확인.
