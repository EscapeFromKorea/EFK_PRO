# PR 제목 규칙: [타입] 간결한 설명
# 예: [FEAT] 플레이어 점프 메카닉 구현 / [FIX] 충돌 감지 버그 수정
# 코드검토 보고서라면: # [PR] <대상 요약> — 코드검토 보고서

> **대상**: 이 PR/보고서가 다루는 대상을 한 줄로 (기능명 또는 검토 범위)
> **브랜치**: `브랜치명` · 커밋 `해시` (여러 건이면 항목별로 나열)
> **작성일**: 작성일 (갱신 시 갱신일과 사유도 함께)
> **성격**: 변경/발견 몇 건 중 몇 건이 이미 반영됐고 몇 건이 남았는지 한 줄 요약

## 변경 사항 (Changes)
> 항목별로 번호를 매긴 하위 섹션으로 쓴다. 각 제목에 상태를 바로 노출한다:
> `### N. <한 줄 요약> (심각도: 상/중/중하/하 — 버그 수정 시) — 수정 완료 / 미반영`
> (신규 기능이면 심각도 대신 생략 가능)
>
> 각 항목 안에는:
> - **코드를 실제로 보여준다.** 말로만 설명하지 말고 코드 블록을 넣는다.
>   - 문제가 되는/기존 코드를 ` ```csharp ` 블록으로 먼저 보여준다. 블록 첫 줄에
>     `// Assets/경로/파일.cs` 주석을 넣어 어디 코드인지 바로 알게 한다.
>   - 적용한 수정도 같은 방식(파일 경로 주석 포함 블록)으로 보여줘서 전/후를 나란히 비교할 수
>     있게 한다.
>   - 한두 줄짜리 사소한 변경(주석 드리프트, 오타 등)은 전/후 블록 대신 ` ```diff ` 블록으로
>     짧게 보여준다(`-`/`+` 한두 줄).
> - "왜 이렇게 했는가" 산문 설명 — 버그면 증상이 어떻게 나타나는지·발생 빈도/조건도
> - 대안이 있었다면 채택한 해결책과 **기각한 대안**을 나란히 적고 이유를 남긴다
>   (`해결책 A — ... (권장, 적용됨)` / `해결책 B — ... (기각)`)
> - 정적 코드 읽기로만 추론한 것과 실측/플레이테스트로 확인한 것을 문장으로 구분한다.
>   확신 없는 항목을 확신 있는 것처럼 쓰지 않는다.

## PR 체크리스트 (Checklist)
> 실제로 안 한 일은 미체크로 남기고 괄호로 사유를 덧붙인다.
> (예: `- [ ] 로컬에서 실행 및 기능 테스트 완료 (Unity 배치모드 컴파일만 확인, 실제 플레이테스트는 미완료)`)

### 제출자 (Author)
- [ ] 로컬에서 실행 및 기능 테스트 완료
- [ ] 관련 이슈 번호 연결
- [ ] 커밋 메시지 컨벤션 준수
- [ ] 불필요한 디버그 로그 / 주석 제거
- [ ] 충돌(Conflict) 없음 확인

### 리뷰어 (Reviewer)
- [ ] 변경 사항 이해 및 의도 파악
- [ ] 코드 로직 검토
- [ ] 직접 빌드하여 테스트
- [ ] 네이밍 / 컨벤션 준수 확인
