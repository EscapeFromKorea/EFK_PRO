> 지정·실측 전. 요구사항 B(CH4 상방 시야)는 CH4 씬이 들어온 뒤 실측과 함께 진행.**

> 거리" 하한은 두지 않았다** — §3.7에 따라 벽이 우선이라, 하한을 두면 좁은 곳에서 카메라가 벽

> 묶은 이유: 위를 보려고 궤도를 내리면 카메라가 바닥 속으로 들어가므로(§2) 두 요구는 같은
> 문제다. 일반 충돌 보정이 없으면 CH4 상방 시야는 성립하지 않는다.

## 1. 기획 의도 / 목적

- **일반(전 맵):** 카메라가 벽·천장·바닥을 뚫어 반대편이 보이거나 플레이어가 가려지는 일을 막는다.
  Notion은 맵2(Kitchen)·맵3(ToyWorld)에서 특히 심하다고 적었다.
- **CH4:** 원통형 수직 공간에서 위쪽 낙석·레이저·다음 착지 지점을 **미리 볼 수** 있어야 한다.
  위층이 보이는 위치와 방향을 함께 만들어야 한다.
- 두 경우 모두 카메라 방향은 플레이어 입력 그대로 두고 **거리만** 줄었다 늘어난다.

## 2. 현재 상태 (코드 확인, 2026-10-04)

| 항목 | 확인 내용 |
|---|---|
| 카메라 | 직접 만든 `PlayerSystem/PlayerFollowCamera.cs`. 패키지에 Cinemachine 없음 |
| 위치 계산 | 추적 지점(SmoothDamp) + `Euler(orbitPitch, orbitYaw, 0) × offset`. 기본 `offset = (0, 4, -10)` |
| 시선 계산 | `dir = up × lookHeightOffset − rotatedOffset`. 타깃의 실시간 위치를 읽지 않는 결정론적 식 (화면 울렁임을 없애려 2026-09-15 바꾼 것) |
| 충돌 처리 | **없음**. 지형 검사 코드가 전혀 없다 |
| 피치 한계 | `minPitch = −50`(올려다보는 쪽), `maxPitch = 60`(내려다보는 쪽). 씬에 직렬화된 값이 코드 기본값보다 우선한다 |
| 레이어 | `TagManager`에 쓰는 레이어가 `Default` 하나뿐. 지형·플레이어·낙석이 전부 `Default` |
| 투석기 조준 카메라 | 별도 카메라 없음. 투석기 코드는 `PlayerFollowCamera`를 호출하지 않는다. 카메라를 따로 바꾸는 조준은 SpacePortal 우클릭 조준(`EnterAimMode`) 하나뿐 |
| 이 카메라를 부르는 쪽 | `SetActiveTarget`(Tab), `SnapToTarget`(리스폰·포탈), `FaceDirection`(포탈 출구), `SetTrackingAnchor`(굴리기), `EnterAimMode`/`ExitAimMode`(포탈 조준), `ViewYaw`/`MouseOrbitActive`(이동·가속·실타래·굴리기가 카메라 상대 이동에 사용) |

### 위를 볼 때 실제 시선 각도 (offset (0,4,−10), lookHeightOffset 1 기준 **산술 계산, 실측 아님**)

| 궤도 pitch | 카메라 높이(플레이어 기준) | 실제 시선의 수평 위 각도 |
|---|---|---|
| −50° (현재 `minPitch`) | −5.1 | **32.7°** |
| −60° | −6.7 | 42.1° |
| −70° | −8.0 | 51.5° |
| −79.2° | −9.1 | 60.1° |
| −90° | −10 | 약 70° |

- Notion의 "실제 시선 약 33°"는 `minPitch −50`의 값과 맞는다. 다만 원문은 이를 `maxPitch`
  값처럼 적었는데, 올려다보는 한계는 `minPitch`다(`maxPitch`는 내려다보는 쪽).
- **60°에 닿으려면 궤도를 약 −79°까지 내려야 하고, 그때 카메라는 플레이어보다 약 9유닛 아래,
  즉 바닥 속이다.** pitch만으로는 −90°에서도 약 70°에서 멈춘다. 80° 이상은 offset 회전만으로
  도달할 수 없다.
- 기존 짐벌락 기록(`atan(|z|/y)` = 68°)은 **내려다보는 쪽** 극점이다. 올려다보는 쪽에는 같은
  극점이 없지만, 시선이 80°에 가까워지면 카메라→시선점의 수평 성분이 수직 성분의 약 0.18배
  (tan 10°)로 줄어 같은 종류의 요동이 생길 수 있다. 실측으로 확인해야 한다.

## 3. 요구사항 A — 일반 지형 가림 방지 (전 맵)

1. 카메라가 원하는 위치를 계산한 뒤, **같은 프레임에** 추적 지점에서 그 위치까지 고정 지형을
   검사한다. 가림이 있으면 지형의 플레이어 쪽 안전 위치에 카메라를 둔다.
   - 포탈 조준 중이면 이미 블렌드된 조준 오프셋을 적용한 위치가 검사 대상이다.
   - 얇은 광선 하나가 아니라 카메라 근접면이 지형에 파고들지 않는 두께의 검사 범위를 쓴다.
2. **당기는 동작은 즉시 또는 매우 빠르게**, 가림이 사라진 뒤 원래 거리로 **돌아가는 동작만
   부드럽게** 한다. 복귀 중 새 벽을 만나면 즉시 다시 당긴다.
3. 모서리에서 가림 판정이 매 프레임 켜졌다 꺼져 카메라가 앞뒤로 왕복하지 않게 한다.
4. 카메라 방향(`orbitYaw`/`orbitPitch`)은 바꾸지 않는다. `orbitYaw`는 `ViewYaw`로 이동 방향
   계산에 쓰이므로 충돌 보정이 이 값을 건드리면 이동 방향이 틀어진다.
5. 시선은 **보정된 오프셋을 기존 결정론적 식에 넣어** 계산한다. 타깃의 실시간 위치를 다시
   읽지 않는다(2026-09-15에 없앤 울렁임이 되살아난다).
6. **충돌 대상(확정): 전용 레이어를 신설**해 고정 지형에만 지정한다. 지형·플레이어·낙석이 전부
   `Default`라 레이어로 가를 수 없기 때문이다. 아래는 대상이 아니다.
   - 트리거 (반투명 포탈, 중력/무중력 버블, 무게 구름 등)
   - 플레이어 도형 자신(`PlayerMover` 계층), 다른 도형
   - 낙석 같은 움직이는 위험물
   검사는 트리거를 무시하고 신설 레이어만 본다.
7. 카메라가 들어갈 공간이 최소 거리보다 좁으면 지형 안으로 통과시키지 않고 가장 가까운 유효
   위치를 택한다. 그 위치에서도 플레이어가 화면에 묻히면 **맵의 벽·계단 간격을 고친다** —
   충돌 보정만으로 막힌 시야를 해결했다고 보고하지 않는다.
8. 지형 가림 방지는 **항상 켜져 있다**(전 맵). 열린 공간의 평소 거리·조작 감도·굴리기 안정성은
   달라지지 않아야 한다.
9. 바닥 방향도 같은 규칙이다 — 카메라가 바닥 밑으로 내려가 바닥 아래가 보이면 안 된다.

## 4. 요구사항 B — CH4 상방 시야

1. **목표 각도:** 합격선은 Notion 본문의 **실제 시선 수평 위 60° 이상**, 시험 목표는 제목의
   1단계인 **80°**(2026-10-04 확정). 85°·90°는 80° 결과를 보고 정한다. **90°(바로 위)는 방향
   계산이 정의되지 않는 극점이라 이 구조에서는 불가능하다** — Notion이 "90도에 문제가 있으면
   말해"라고 한 것에 대한 답이 이것이다.
2. 인스펙터의 `minPitch` 숫자만 바꿔 완료로 취급하지 않는다. **실제 카메라 forward의 수평 위
   각도**를 측정해 판정한다.
3. 카메라를 도형보다 크게 아래로 내려 바닥 속에 숨기는 방식은 쓰지 않는다. 시선과 카메라 궤도를
   분리하거나, 원하는 궤도 위치를 요구사항 A의 충돌 보정으로 바로잡아 위층이 보이는 위치와
   방향을 함께 만든다. 구체 방식은 구현 시 실측으로 정한다(§2의 표가 출발점).
4. 도형도 시야에 남아야 한다 — Notion §4 확인 항목은 "계단 아래에서 위층 위험과 조작 도형이
   동시에 보이는지"다. 수직 FOV는 `SampleScene` 카메라 기준 60°다.
5. 도형(네모 텀블·세모 굴리기)의 회전은 카메라 시선에 섞지 않는다.
6. **CH4 전용 시야 범위의 적용 조건:** **현재 조작 중인 도형**이 CH4 구역에 있을 때.
   구역을 나가면 기존 평지 값으로 돌아간다. Tab으로 다른 도형을 조작하면 새 조작 도형이 있는
   구역 기준으로 바뀐다.
7. 높은 각도에서 CH4를 나갈 때 새 한계 밖의 각도는 갑자기 꺾지 않고, 인스펙터에서 조절 가능한
   **CH4 프로필 전환 시간** 동안 부드럽게 제한한다.
8. 구역 판정은 도형의 **위치**로 한다(트리거 콜백에 의존하지 않는다). 저장소의 `TeamExitZone`이
   "잠든 Rigidbody에는 `OnTriggerStay`가 오지 않는다"는 이유로 위치 질의를 쓰는 것과 같은 이유다.

## 5. 보존해야 하는 기존 동작

| 기존 동작 | 요구 |
|---|---|
| 굴리기 기준점 블렌드 (`SetTrackingAnchor`) | 입력 유지. 충돌 검사는 블렌드된 추적 지점 기준 |
| 포탈 조준 (`EnterAimMode`) | 조준 구도·입력 우선, **지형 가림 검사는 계속** |
| Tab 전환 (`SetActiveTarget`) | 새 도형·새 지형에서 즉시 유효 위치를 계산. 이전 거리 보간값을 끌고 오지 않는다. 전환 중 카메라가 벽에 걸리는 경우도 시험 |
| 리스폰·포탈 스냅 (`SnapToTarget`) | 스냅 직후 지형 검사를 적용하고 이전 당김 상태를 지운다. 스냅식과 `LateUpdate` 식이 갈라지면 한 프레임 튄다(기존 주석 경고) |
| 포탈 출구 시점 (`FaceDirection`) | 입력 유지 |

| 크기 변형(ScalingSystem) | 도형이 커지거나 작아질 때 최소 거리·충돌 반경이 같이 맞는지 확인 |
| CH4 밖 | 상방 시야 범위만 기존 값으로 복귀. 평지의 카메라 거리·감도·굴리기 안정성은 그대로 |

## 6. 레이어·배치

- 새 레이어는 `ProjectSettings/TagManager.asset`에 추가한다. 이름은 구현 시 정한다(미정).
- **기존 씬의 고정 지형 오브젝트에 레이어를 지정해야 한다.** 지정이 빠진 지형은 카메라가
  그대로 통과한다. Notion §3은 "충돌 대상 목록에서 빠졌다면 설정 오류를 찾을 수 있어야 한다"고
  요구하므로, 누락을 찾는 수단(에디터 검사 메뉴 또는 기즈모)이 필요하다. 방식은 미정이다.
- 씬 수정은 저장소 전례를 따른다: `SampleScene.unity`는 텍스트 머지·임의 되돌리기 금지,
  배치모드 `SaveScene`은 무관한 오브젝트까지 대량 재직렬화한다(메모리 기록). 레이어 지정
  방식은 구현 시 정한다.
- `PlayerFollowCamera`는 `PlayerSystem`(플레이어 코어)에 있다. 구현은 이 폴더를 수정하므로
  **착수 전 사용자 허가를 확인한다**(저장소 하드 룰). CH4 구역 컴포넌트를 둘 폴더도 구현 시
  정한다(미정).
- **현재 브랜치의 `Assets/Scenes`에는 `SampleScene`·`Lab_CH1`·`Lab_CH2`·`GimmickDemo_mnppi`만
  있다.** 맵2·맵3·CH4 씬은 이 브랜치에 없으므로, 해당 씬에서의 시험은 그 씬이 들어온 뒤에 한다.

| C-07 | CH4 열린 공간에서 위로 끝까지 올림 | **실제 시선 60° 이상**(목표 80°), 요동·뒤집힘 없음 |
| C-08 | CH4 원통 벽·계단 아래·계단 옆 모서리·반중력 상승 경로 | 카메라가 지형 안으로 들어가지 않고, 도형과 다음 위험이 함께 보인다 |
| C-09 | CH4 진입 → 이탈 → 재진입, 높은 각도에서 이탈 | 시야 범위와 거리가 이전 구역 값에 남지 않는다. 각도는 전환 시간 동안 부드럽게 제한 |
| C-10 | 각 도형으로 굴리기·Tab·리스폰·포탈 조준 수행 | 기존 조작 유지 |
| C-11 | 리스폰·멀리 있는 도형으로 Tab 전환 | 이전 보간값 없이 새 위치에서 즉시 유효 위치 |
| C-12 | 챕터 전체 재시작 | 이전 벽의 가림 거리와 CH4 프로필 잔여값이 지워지고, 복귀한 도형의 현재 구역을 다시 읽는다 |
| C-13 | 고정 지형에 레이어를 안 준 오브젝트가 있음 | 설정 오류를 찾을 수 있다(§6) |
| C-14 | 60° 시야가 가능한 열린 공간 시험과 원통 배치로 시야가 가려지는 시험 | **따로 기록**(Notion §5) |

## 전체 재시작 처리

챕터 전체 재시작 때 이전 원통 벽의 가림 거리와 CH4 프로필 잔여값을 지운다. 복귀한 조작 도형의
현재 구역을 다시 읽고 그 위치에서 올바른 프로필과 충돌 거리를 계산한다. 같은 시도 안의 개인
복귀는 `SnapToTarget`을 따른다(§5).
