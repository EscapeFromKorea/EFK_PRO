# 레일카 (Rail Cart) — PRD

> 태엽 축(`WindupAxleSystem`) 파생 장치 2호. `docs/PRD/WindupAxle.md` §5가 "이동/탑승 로직이
> 커서 이후로 미룬다"고 명시했던 그 레일카를 다루는 문서다. 1호(`RotatingPlatform`)와 달리
> 여기서 처음 나오는 요구(탑승, 적재, 탈선, 와이어 견인)가 많아 결정할 지점이 크다.
> 상태: **1차 구현 + 씬 배치 완료, 실측 진행 중(2026-09-05).** 1차 플레이테스트 피드백을 반영한
> 재설계까지 마쳤다 — RotatingPlatform과 같은 지연 발동(§3.1), 곡선 레일(§3.4a), 철도 시각화
> (§3.4b), U자형 광산차 외형(§3.2a), C키 탑승/하차(§3.2b). 상세는 각 절 "2026-09-05 재설계" 참고.

## 1. 원본 기획 요구사항 (참고용 원문)

```
기능:
태엽 동력으로 레일을 달리며, 탑승·적재·탈선·와이어 견인이 가능한 물리 오브젝트다.

요구사항:
- 태엽 축의 정방향·역방향 동력으로 전진과 후진한다.
- 플레이어가 탑승하거나 직접 밀 수 있어야 한다.
- 딱딱 블록을 적재할 수 있어야 한다.
- 기존 와이어의 동적 앵커로 사용할 수 있어야 한다.
- 레일 위에서는 안정적으로 주행하지만 특정 속도나 분기에서는 탈선할 수 있어야 한다.
- 탈선 직후 자동 삭제하거나 즉시 원위치시키지 않는다.
- 낙하·완전 전복 등 더 이상 사용할 수 없는 경우에만 복구한다.
- 최고 속도, 구동력, 레일 복원력, 탈선 조건을 조절할 수 있어야 한다.

주요 활용:
- 정상 탑승 이동
- 탈선시켜 계곡의 다리로 사용
- 블록을 실어 시소에 충돌
- 와이어를 걸고 끌려가다 관성으로 착지

완료 조건:
- 정상 운행·탈선 다리·와이어 견인 세 풀이가 실제로 가능하다.
- 탈선 후에도 다리·발판·추로 사용할 수 있다.
- 블록 적재량이 카트의 가속과 충돌에 영향을 준다.
```

사용자 확인(2026-09-05): "기존 와이어" = `DreamThreadSystem`(`ThreadAnchor`)이고,
"딱딱 블록"은 **다른 사람이 구현할 별도 기믹 시스템**(현재 저장소에 없음, 이 문서 범위 밖)이다.

## 2. 기획 의도 / 목적

`WindupAxle`은 파생 장치가 무엇인지 모른 채 신호(`outputPower`, `chargeRatio`)만 내보낸다
(`WindupAxle.md` §1). 1호 `RotatingPlatform`은 그 신호를 제자리 회전으로 소비하는 가장 단순한
소비자였다면, 레일카는 **이동 + 탑승 + 상태 전이(온레일 ↔ 탈선)**까지 겹친 훨씬 무거운 소비자다.

이 기믹을 다른 파생 장치와 구분 짓는 핵심은 **"탈선이 실패 상태가 아니다"**라는 점이다. 다른
기믹(예: `DestructionSystem`)은 "부서지면 편도, 복구 없음"이라 진행 필수 경로에 두면 안 되는
반면, 레일카는 탈선한 뒤에도 다리·발판·추로 계속 쓰인다 — 즉 **레일카의 수명 주기 자체가
퍼즐 요소**다. "낙하·완전 전복"이라는 아주 좁은 조건에서만 복구가 일어나고, 그 외에는 사용자가
탈선체를 계속 활용하도록 방치하는 것이 설계 의도다.

## 3. 동작 시나리오

### 3.1 온레일 구동 (태엽 동력)

`RailCart`가 `IWindupReceiver.ApplyOutput(power, ratio)`를 구현해 신호를 받는다. `power`의
부호가 레일 진행 방향(+ = 정방향/전진, - = 역방향/후진)을, `ratio`가 목표 속도/가속에 대한
배율을 결정한다 — `RotatingPlatform`이 `power`를 회전 목표각으로 소비하는 것과 같은 구조를
"레일을 따라가는 위치 파라미터"로 바꿔 소비한다.

**지연 발동 — 확정(2026-09-05, RotatingPlatform과 동일 규칙).** 1차 플레이테스트 후 "레일카도
회전판처럼 태엽을 마지막으로 감은 시점 기준 3초 뒤에 작동해야 한다"는 피드백을 반영했다.
`OnCrankSwing`(한 번 밀 때마다 호출되는 이산 이벤트)이 `lastSwingTime`을 갱신하고,
`Time.time - lastSwingTime >= releaseDelay`(기본 3초)가 될 때까지 구동력(`AddForce`)을 걸지
않는다 — 그 사이 또 밀면 타이머가 다시 시작된다(`RotatingPlatform.releaseDelay`와 정확히 같은
규칙). 다만 회전판처럼 걸음 단위로 끊어 돌지는 않는다 — 지연이 풀리면 `ApplyOutput`의 연속
방전 곡선을 그대로 타는 연속 구동력을 쓴다("감았다 서서히 풀리며 굴러간다"는 태엽 느낌이 물리
차량에 더 맞기 때문).

### 3.2 탑승 · 직접 밀기

- **직접 밀기**: 태엽 동력 없이도 플레이어가 카트에 물리적으로 부딪혀 미는 힘만으로 굴러가야
  한다 — 즉 카트는 항상 dynamic Rigidbody여야 하고(`FallingRockSystem`처럼 velocity 대입 금지
  원칙을 여기도 적용), 온레일 구동은 "레일 방향으로의 힘/속도 보정"이지 위치를 직접 대입하는
  방식이면 안 된다.

**탑승 — 확정(2026-09-05, 1차 플레이테스트 후 C키 방식으로 재설계).** 처음엔 `CatapultSystem`의
버킷 트리거 패턴(걸어서 올라타면 자동 탑승)을 재사용했지만, 사용자가 "그 근처에서 C키를 눌러
탑승/하차"하는 방식으로 바꿔 달라고 확정했다 — `CatapultBucket`의 C키 거리 게이트(근접 + 텔레포트
+ 부모화 + `isKinematic`) 패턴을 그대로 가져오되 발사(launch) 개념은 없다. 카트가 곡선 레일에서
위치뿐 아니라 방향도 계속 바뀌므로, velocity만 얹어 따라가게 하는 방식(직선에서만 맞음)보다
완전 종속(부모화)이 회전까지 자동으로 따라가 더 정확하다. **카트 루트 Transform은 항상
`localScale=(1,1,1)`을 유지한다** — 비균일 스케일에 회전이 겹치면 부모화 시 전단(shear)이 생겨
탑승자가 찌그러지는 문제를 `CatapultBucket`이 이미 겪었기 때문에(`CatapultSystem/CLAUDE.md`
"10차 개편"), 처음부터 그 함정을 피하도록 설계했다 — 외형(U자형 광산차 몸체)은 전부 자식
오브젝트의 로컬 스케일로만 표현한다.

**외형 — U자형 광산차(2026-09-05 확정).** 단순 박스 대신 열린 위(바닥판 + 좌우/앞뒤 벽)로 된
작은 광산 수레 모양으로 바꿨다 — 물리 콜라이더는 카트 루트의 `BoxCollider` 하나가 전담하고,
벽/바닥/바퀴(좌우 2개, `CatapultSystem`의 손수레 바퀴와 같은 단순화)는 전부 콜라이더 없는
순수 시각 자식이다.

### 3.3 적재 (딱딱 블록)

카트에 화물 트리거 영역을 두고, 그 안에 들어온 Rigidbody의 질량을 합산해 가속·충돌 세기에
반영한다. "딱딱 블록"은 이 문서 범위 밖의 별도 기믹이므로, 카트는 **그 시스템이 무엇인지
전혀 몰라야 한다** — `DestructionSystem`이 `PlayerWeight.Of` 같은 전용 함수 대신 순수
`Rigidbody.mass`로 운동량을 재는 것과 같은 이유로, 여기서도 특정 컴포넌트 타입을 찾지 않고
트리거 안의 아무 Rigidbody나 질량 합산 대상으로 삼는다(가칭 `RailCartCargoBay`). 블록
시스템이 나중에 들어와도 카트 쪽 코드를 고칠 필요가 없다.

### 3.4 탈선 · 복구

**탈선 조건 — 확정(2026-09-05): "속도 임계"와 "분기"를 별개 규칙으로 두지 않는다.** 웨이포인트
배열이라 카트는 항상 "지금 어느 구간(웨이포인트 i → i+1)에 있는지" 안다. 구간마다
`maxSafeSpeed`를 하나씩 두고(직선 구간은 크게/사실상 무제한, 급커브·분기 구간은 레벨
디자이너가 낮게 잡음), **현재 속도가 그 구간의 `maxSafeSpeed`를 넘으면 탈선**한다는 검사
하나로 끝낸다. "분기에서 탈선"은 이 규칙의 특수 케이스가 아니라 — 그냥 안전 속도를 낮게 잡아둔
구간일 뿐이다. 카트는 조향 입력이 없으므로(태엽 동력만으로 구동) 확률 기반 판정 같은 별도
분기 로직은 넣지 않는다.

- 탈선 조건을 만족하면 카트는 레일 추종을 끊고 **순수 물리 객체**로 전환된다 — 즉시 삭제·즉시
  원위치 금지(요구사항 원문).
- 복구는 "낙하"(월드 밖으로 이탈 — `RespawnSystem`의 킬 라인과 유사한 판정을 재사용할 수
  있음) 또는 "완전 전복"(뒤집혀 스스로 못 일어나는 상태) 두 조건에서만 발생한다. 그 외에는
  탈선된 채로 씬에 영구히 남아 다리·발판·추로 쓰인다.

**"완전 전복" 판정 — 확정(2026-09-05).** 기울기(`Vector3.Angle(transform.up, Vector3.up)`,
0=직립·180=완전히 뒤집힘)가 `overturnAngleThreshold`를 넘는 동안 타이머를 누적하되, **버텨야
하는 시간을 고정값이 아니라 기울기가 클수록 짧아지는 값**으로 계산한다 — 살짝 걸친 채면 오래
버티다가만 판정하고, 완전히 뒤집혔으면 금방 판정해 "더 확실히 뒤집힐수록 빨리 포기한다"는
현실적인 느낌을 낸다. 지속 시간 자체가 이미 "회전 중"과 "멈춰서 뒤집힘"을 구분해준다(진짜로
구르는 중이면 각도가 계속 바뀌어 임계 위에 연속으로 안 붙어 있는다) — 별도 각속도 조건은
필요 없다.

```csharp
float tiltAngle = Vector3.Angle(transform.up, Vector3.up); // 0~180

if (tiltAngle < overturnAngleThreshold) { overturnTimer = 0f; return; }
overturnTimer += Time.deltaTime;

// severity: threshold(=0)~180도(=1) 사이 진행률. 기울수록 1에 가까워진다.
float severity = Mathf.InverseLerp(overturnAngleThreshold, 180f, tiltAngle);
// 필요 지속시간: 임계값 근처면 overturnHoldSecAtThreshold(길게), 완전히 뒤집히면
// overturnHoldSecAtFullFlip(짧게)까지 선형 보간.
float requiredHold = Mathf.Lerp(overturnHoldSecAtThreshold, overturnHoldSecAtFullFlip, severity);

if (overturnTimer >= requiredHold)
    BeginOverturnRecovery(); // 이후 overturnRecoveryDelaySec만큼 더 기다렸다가 실제 복구
```

`overturnRecoveryDelaySec`(§5)는 이 판정과 별개다 — "뒤집혔다고 확정된 뒤"에도 바로 순간이동
시키지 않고 한 번 더 유예를 주는 연출용 지연이다(요구사항의 "즉시 원위치시키지 않는다"를
전복 확정 이후 구간에도 동일하게 적용).

### 3.4a 곡선 레일 (2026-09-05 추가)

`RailPath`가 확정한 "웨이포인트 배열" 결정(§6) 자체는 바뀌지 않았다 — 분기·탈선 판정은 여전히
구간별 `maxSafeSpeed` 하나로 코드가 완전히 결정한다. 다만 구간 "안"의 모양은 이제 직선만이 아니다
— 구간마다 선택적 제어점(`curveControlPoints[i]`)을 꽂으면 그 구간이 2차 베지어 곡선으로 휜다
(제어점을 비워두면 기존과 동일한 직선). 카트는 매 물리 틱 실제 위치에서 현재 구간 위 최근접
매개변수(t)를 샘플링으로 다시 찾아(`RailPath.ClosestT`) 그 지점의 접선 방향으로 밀고 그 지점으로
옆 이탈을 되돌린다 — 별도의 누적 진행값을 따로 들고 다니지 않아 직접 밀려도 자연히 보정된다.
`AnimationCurve`를 분기 표현 문제로 기각했던 §6의 판단과 모순되지 않는다 — 여기서 휘는 건
"구간 내부의 모양"일 뿐, 구간을 잇는 순서·탈선 판정은 여전히 웨이포인트 배열 그대로다.

### 3.4b 철도 시각화 (2026-09-05 추가)

레일이 추상적인 웨이포인트 선이 아니라 실제 철도처럼 보이도록 `RailTrackVisual`을 추가했다 —
두 `LineRenderer`로 궤간만큼 떨어진 레일 두 줄을 곡선 그대로 그리고, 그 사이에 침목(sleeper)
큐브를 일정 간격으로 깐다. 콜라이더가 없는 순수 시각 컴포넌트라 물리에 전혀 관여하지 않는다.
에디터에서 웨이포인트나 곡선 제어점을 옮기면 즉시 다시 그려져(`[ExecuteAlways]`) 곡선을
저작하는 동안 바로 피드백을 준다.

### 3.5 와이어 견인 (DreamThreadSystem 동적 앵커) — **해결됨 (2026-09-05, 사용자 허가 하에
`DreamThreadSystem` 수정)**

카트에 `ThreadAnchor`를 자식으로 붙여 플레이어가 F로 걸면 된다. 원래는 `DreamThreadController`가
연결 순간의 월드 좌표를 `joint.connectedAnchor`에 한 번만 찍어두고 이후 앵커가 움직여도 따라가지
않는 구조라("핀 GameObject를 물리적으로 참조하지 않는다"는 기존 설계, `DreamThreadSystem/CLAUDE.md`
참고) 레일카처럼 계속 움직이는 앵커에 걸면 실이 처음 위치에 고정된 채 카트만 멀어지는 문제가
있었다.

**원인을 더 보니 이미 반쯤 고쳐져 있었다** — 펌핑 계산(`rope = activeBody.position -
anchor.transform.position`)과 실 렌더링(`LateUpdate`의 `anchor.transform.position`)은 이미 매
프레임 앵커의 최신 위치를 읽고 있었고, 물리 구속(`joint.connectedAnchor`)만 연결 순간에
박제돼 있었던 것 — 지금까지 모든 앵커가 정적이라 드러나지 않았던 기존 버그였다. 그래서
`DreamThreadController.FixedUpdate()`에 `joint.connectedAnchor = anchor.transform.position;`
한 줄만 추가해 물리 구속도 매 프레임 앵커를 따라가게 했다(정적 앵커는 매번 같은 값을 다시 쓰는
것뿐이라 동작 변화 없음, 새 필드·옵트인 플래그 불필요). `ThreadCubeAnchor`(네모 닻)가 연결 후
밀리면 매달린 사람도 같이 끌리게 되는 부수효과가 생기지만, 예외 처리 없이 전체 앵커에 동일 적용
하기로 확정했다(오히려 "네모가 버텨준다"는 기획 의도에 더 맞는 쪽으로 판단).

## 4. 컴포넌트 / 스크립트 설계 (초안, 확정 아님)

저장소 공통 발신자-수신자 분리 패턴을 따르되, `WindupAxle`이 자신을 신호원으로 보는 것처럼
레일카도 "레일 위 이동 상태"와 "탑승/적재/견인"을 분리해 응집도를 지킨다.

- **`RailCart`** — 본체. `IWindupReceiver.ApplyOutput(power, ratio)` 구현, 레일 추종/탈선/
  복구 상태 머신 보유. 항상 dynamic Rigidbody.
- **`RailPath`** (가칭) — 레일 자체. **웨이포인트 배열(`Transform[]`) + 진행 매개변수 `t`로
  확정(2026-09-05)** — `Vector3.Lerp(waypoints[i], waypoints[i+1], frac)`로 온레일 위치를
  코드로 완전히 결정한다. 분기점은 한 웨이포인트에 다음 후보가 여럿인 노드로 표현하고, 탈선은
  "이 지점에서 `t` 갱신을 멈추고 Rigidbody를 dynamic으로 되돌린다"는 한 지점짜리 전환으로
  끝난다. `AnimationCurve`는 분기 표현이 근본적으로 안 맞고(시간→값 단일 함수), 실제 트랙
  메쉬 위 물리 주행은 저장소가 `PortalSystem`/`PlayerMover`에서 이미 두 번 겪은 "스크립트와
  PhysX 솔버가 다면체 회전/위치를 동시에 소유"하는 결정론 붕괴 패턴을 반복할 위험이 커서
  기각했다. 구간(웨이포인트 i → i+1)마다 `maxSafeSpeed`를 갖는다(§3.4) — "속도 임계"와
  "분기 탈선"이 이 필드 하나로 통합된다. **2026-09-05 추가** — 구간마다 선택적 곡선 제어점
  (`curveControlPoints[i]`)을 가질 수 있다(§3.4a).
- **`RailTrackVisual`** (2026-09-05 신규) — `RailPath`가 붙은 오브젝트에 함께 달아 철도처럼
  보이게 하는 순수 시각 컴포넌트(§3.4b). 물리에 관여하지 않는다.
- **`RailCartRider`** — 탑승/하차. **2026-09-05 재설계** — 걸어서 올라타는 트리거 대신
  `CatapultBucket`의 C키 거리 게이트(§3.2)로 바뀌었다. 카트 루트에 직접 붙는다(별도 트리거
  자식 불필요).
- **`RailCartCargoBay`** (가칭) — 화물 트리거. 안의 Rigidbody 질량 합산 → `RailCart`에 통지.
- 와이어 앵커: `ThreadAnchor`를 카트 자식으로 배치(§3.5, 동적 추적은 `DreamThreadController`
  쪽 수정으로 해결됨). **아직 씬에 배선하지 않았다** — 코드/설계만 준비됨.

## 5. 확정값 / 기본값 (전부 씬 튜닝 대상)

| 파라미터 | 설명 |
|---|---|
| `releaseDelay` | 축을 마지막으로 민 시점부터 구동력이 걸리기까지의 지연(초) — `RotatingPlatform.releaseDelay`와 같은 규칙(2026-09-05) |
| `maxSpeed` | 레일 위 최고 속도 |
| `drivingForce` | 태엽 신호 1당 구동력 |
| `railRestoreForce` | 레일에서 살짝 벗어났을 때 되돌리는 힘(탈선과는 별개 — "안정적으로 주행"의 근거) |
| `RailPath` 구간별 `maxSafeSpeed` | 그 구간(웨이포인트 i→i+1)에서 이 속도를 넘으면 탈선(직선은 크게, 급커브·분기는 작게 — 레벨 디자이너가 구간마다 지정) |
| `cargoMassMultiplier` | 적재 질량이 가속/충돌 세기에 반영되는 계수 |
| `overturnAngleThreshold` | 전복 판정을 시작하는 최소 기울기(도) |
| `overturnHoldSecAtThreshold` | 기울기가 임계값에 막 걸쳤을 때 버텨야 하는 시간(김) |
| `overturnHoldSecAtFullFlip` | 완전히 뒤집혔을 때(180도) 버텨야 하는 시간(짧음) |
| `overturnRecoveryDelaySec` | 전복/낙하 "확정" 후 실제 복구까지 추가 유예 시간 |
