## 1. 무엇을 위한 기믹인가

포탈을 통과하면 그 도형의 **이동 방식 자체가 바뀐다.** 지금까지의 기믹이 "속도를 더한다 / 띄운다 / 막는다"였다면, 이건 **조작 규칙을 갈아끼우는** 첫 기믹이다.

바뀐 방식은 **모서리를 축으로 한 칸씩 넘어가는 격자 텀블**이다. 주사위를 굴리듯 정확히 한 모서리분만 이동하고, 중간 자세는 없다.

- **포탈은 순간이동을 하지 않는다.** 문틀을 지나는 것뿐이고 위치는 그대로다. 이동 방식만 바뀐다.
- **입구 포탈과 출구 포탈이 한 쌍**이다. 그 사이 구간에서만 굴리기가 유효하다.
- **선택 경로 전용이다.** 메인 진행에 필수인 구간에는 배치하지 않는다(§11).

## 3. 왜 "이산 스텝 텀블"인가

이 저장소는 모서리 굴리기를 **이미 두 번 시도했다가 걷어냈다.** 세 번째 시도가 되므로, 앞선 두 번이 왜 실패했고 이번 방식이 그 원인을 어떻게 제거하는지가 이 절의 전부다.

### 3.1 폐기된 1차 — `RollMode.EdgeTumble`

모서리 피벗 스텝 텀블을 **dynamic 바디 위에서** 시도했다. 다면체가 바닥에 *면*으로 밀착한 상태에서 각속도를 강제하면, 접촉면 양 끝 코너가 동시에 반대 방향(하나는 파고들고 하나는 뜨려)으로 움직이려 해 PhysX 접촉 솔버와 매 스텝 충돌했다. 회전이 거의 안 보이거나 씹혔다.

### 3.2 폐기된 2차 — `PlayerMover.useTorqueRolling`

원인(토크)을 주고 지면 마찰이 실제 구르기로 변환하게 했다. 물리적으로는 옳은 접근이었지만 **각운동량을 솔버가 소유하는 바람에 조향이 되지 않았고**, `SteerAngularVelocity` / `RealignHorizontalVelocity` / `turnAssist` 3중 보정으로 되받아쳐야 했다. 그 보정들이 다시 "구르는 물리감"을 깎아, 얻으려던 것과 치른 비용이 서로를 상쇄했다.

**코드는 아직 `PlayerMover`에 살아 있다**(기본값 `false`, `PlayerObjectMenuItem`이 더 이상 켜지 않음). 씬의 플레이어 3종 모두 `useTorqueRolling: 0`.

> ⚠️ **함정 경고.** 코드가 남아 있어 "플래그만 켜면 된다"는 착수 비용 0으로 보인다. **두 번 걷어낸 이유는 코드 부재가 아니었다.** 솔버도, 접촉 지오메트리도, 고마찰 그립 PhysicMaterial도 그대로다.

### 3.3 이산 스텝이 그 원인을 제거하는 방식

두 실패의 공통 원인은 하나다 — **"평면 접촉 다면체의 회전을 스크립트와 PhysX 솔버가 동시에 소유"**.

이산 스텝 텀블은 **텀블이 도는 동안 `isKinematic = true`로 두어 솔버에게 회전 발언권을 아예 주지 않는다.** 그리고 텀블 사이 휴지기의 몸은 면으로 정상 착지한 합법 자세라, 충돌이 발생할 상태 자체가 존재하지 않는다.

부수 효과로 **조향 보정 코드가 통째로 불필요해진다** — 각운동량이라는 상태가 없기 때문이다. 매 텀블은 시작 자세와 끝 자세가 확정된 유한 애니메이션이다.

### 3.4 폐기된 대안 — 순수 연출 모드

물리·이동 규칙은 그대로 두고 `PlayerVisualRoll`을 확장해 시각 메쉬만 모서리 피벗으로 넘어가게 하는 안. 리스크 0, 규격표 무변화, 구현 비용 최소.

**폐기 사유:** "움직임 방식이 완전히 바뀐다"는 이 기믹의 존재 이유를 충족하지 못한다. 조작 규칙이 하나도 안 바뀐다.

### 3.5 폐기된 대안 — 연속 물리 텀블 재시도

§3.2의 부활. **결정적 폐기 사유는 정사면체다** — 연속 물리에는 "지금 유효한 방향 3개"라는 개념이 존재할 수 없으므로 §4.2의 정사면체 규칙을 **원리적으로 표현할 수 없다.** 덧붙여 `FreezeRotation` 해제는 도달 규격표를 "그 구간만"이 아니라 **그 도형 전체에서** 흔든다.

## 4. 도형별 규칙

### 4.1 정육면체 — 사각격자 4방향

| | 값 |
|---|---|
| 모서리 길이 | 1.0 U |
| 텀블각 | 90° |
| 1칸 이동거리 | **1.0000 U** |
| 이동 방향 | 4방향(월드 축 정렬) |
| 직진 | 가능 |

**정육면체만 텀블 후에도 콜라이더가 축 정렬(90°의 배수)을 유지한다.** 즉 휴지기의 접촉 형상·접지 판정·`BoxCollider` 기하가 텀블 전과 완전히 동일하다. 이 성질이 안전성을 지탱한다.

**텀블이 끝나면 Root 회전을 identity로 스냅한다.** 정육면체는 90° 배수에서 시각적으로 동일하므로 무해하다.

> **[2026-08-19 정정] 원래 적어둔 근거는 이미 죽은 코드였다.** "`ScalingSystem`의 X/Y 독립 스케일 축이 90°마다 뒤바뀌어 납작해지기가 옆으로 납작해진다"고 썼으나, `PlayerShapeController.RecomputeTargetScale`은 **X/Y/Z에 같은 배율만 곱한다**(완전 균일 1:1:1). 납작해지기 자체가 현재 코드에 없고, `useAverageColliderScale`도 런타임에는 아무것도 하지 않는 잔재다.
>
> 스냅은 그대로 유지하되 **근거는 "정준 자세 유지"다** — Root 회전이 identity여야 (1) `PlayerVisualRoll`이 전제하는 "Root 회전 identity라 월드축 = 로컬축"이 모드 이탈 후에도 성립하고, (2) 자식 3개(로컬 회전 identity)와의 관계가 텀블 전후로 불변이며, (3) 누적 부동소수 오차가 매 텀블 0으로 리셋된다. 균일 스케일이라 §6.3의 `(시작+종료)/2`도 축 뒤바뀜 없이 그대로 성립한다.

### 4.2 정사면체 — 삼각격자 3방향 60° 교대

| | 값 |
|---|---|
| 모서리 길이 | √2 = **1.4142** U |
| 텀블각 | **109.47°** (= 180° − 이면각 70.53°) |
| 1칸 이동거리 | **0.8165 U** (= √⅔ = a/√3) |
| 이동 방향 | 한 번에 3개, 총 6개 |
| 직진 | **불가능** |

밑면이 정삼각형이라 모서리가 3개뿐이고, 한 칸 굴리면 밑면이 뒤집혀(▲↔▼) 방향 세트가 **60° 회전**한다. 저장소의 실제 메쉬(`TetrahedronMeshGenerator`) 기준 실측값:

```
상태 A:  45° / 165° / 285°   ← 한 칸 굴리면
상태 B: 105° / 225° / 345°   ← 한 칸 굴리면 다시 A
(0° = +Z 정면, 시계방향)
```

**같은 방향으로 두 번 연속 갈 수 없다.** "앞으로 가려면" 60° 벌어진 두 방향을 번갈아 밟아야 하고, 그 결과:

- 순 진행 방향은 두 방향의 중간 — 총 6개(**15° / 75° / 135° / 195° / 255° / 315°**)
- **월드 축(0°/90°/180°/270°)으로는 아예 갈 수 없다**
- 2스텝 순 이동거리는 직진 대비 **0.866배**
- 중심이 좌우로 **0.408 U** 흔들린다

**입력 처리:** 방향 입력을 **현재 유효한 3방향 중 가장 가까운 것으로 스냅**한다. 스냅 허용 각도를 벗어나면(경계에 애매하게 걸치면) 아무것도 하지 않는다.

> ⚠️ **[2026-08-19 추가] 위 각도표는 "월드 각도"이고, 입력은 월드축이 아니다.** `PlayerMover`는 `(h, 0, v)`를 그대로 쓰지 않고 **`inputYawOffset`만큼 월드 up 축으로 회전시킨 뒤** 쓴다(`PlayerMover.cs:267`, `:458`). 씬의 플레이어 3종 모두 이 값이 **90**이다(`SampleScene.unity:9418, 11105, 13093`). 리시버가 같은 보정을 적용하지 않으면 W가 90° 어긋난 방향으로 굴러간다 — 그런데 정사면체는 어차피 월드축으로 못 가므로(§9.3) **증상이 "원래 그런 기믹인가?"로 보여 잡기 어렵다.**
>
> 입력 → 월드 방향 변환은 반드시 `PlayerMover`와 같은 식을 쓴다: `Quaternion.AngleAxis(mover.inputYawOffset, Vector3.up) * new Vector3(h, 0f, v)`. 값을 복제해 상수로 박지 말고 **`mover.inputYawOffset`을 읽어라** — 씬에서 조정되는 값이다.
>
> **`GetAxis`가 아니라 `GetAxisRaw`를 쓴다.** `PlayerMover`는 스무딩된 `GetAxis`를 쓰는데(연속 이동엔 그게 맞다), 이산 스텝에서는 키를 누른 첫 프레임의 값이 아직 0에 가까워 **첫 텀블의 방향 스냅이 엉뚱한 쪽으로 걸린다.** 스냅은 "지금 어느 키를 눌렀나"의 문제이므로 원시 입력이 맞다.

**콜라이더 월드 형상은 A/B 두 상태로 닫힌다.** 120° 회전은 정사면체 자기 대칭이라 형상이 같기 때문이다. 정육면체가 90° 배수에서 항상 같은 것처럼, 정사면체는 2상태 교대로 결정론이 유지된다. **다만 identity 스냅은 불가능하다** — 대신 A/B 두 정준 자세 중 하나로 스냅한다.

### 4.3 구는 제외한다

구는 이미 자유회전으로 굴러간다. 격자 텀블을 씌워도 시각적 변화가 없고 자유도만 잃는다. **포탈을 통과해도 아무 일도 일어나지 않는다**(막지 않는다 — 그냥 지나간다).

### 4.4 왜 무게 게이트가 아니라 `Kind` 판별인가

**`Assets/CLAUDE.md`의 "무거워서 못 한다류는 `Kind`가 아니라 무게로" 원칙과 형식상 충돌한다. 의도적이며, 근거는 `HourglassSystem`과 같다.**

90° 텀블 가능 여부는 **무게로 잴 수 있는 물리량이 아니라 기하 조건**이다. 무중력 버블로 가벼워진다고 정사면체가 90° 텀블을 할 수 있게 되지 않고, 무거워진다고 정육면체가 못 하게 되지도 않는다. 단조 임계로 나눌 수 없는 역할 분담이므로 `PlayerShapeIdentity.Kind`가 맞다.

## 5. 셀 크기는 노브가 아니다

### 5.1 도출된 수치

한 칸 이동거리는 **도형의 모서리 길이에서 기하학적으로 도출된다.** 그 외의 값은 물리적으로 불가능하다.

| | 정육면체 | 정사면체 |
|---|---|---|
| 모서리 길이 | 1.0 U | 1.4142 U |
| **1칸 이동거리** | **1.0000 U** | **0.8165 U** |
| 정지 시 전체 높이 | 1.0 U | 1.1547 U |
| **텀블 중 최대 천장 소요** | **1.4142 U** | **1.2247 U** |
| 정지 시 중심 높이 | 0.5 U | 0.2887 U |
| 텀블 중 최대 중심 높이 | 0.7071 U | 0.5 U |

*(씬의 플레이어 3종 모두 `localScale (1,1,1)` 확인 — 위 수치가 그대로 적용된다.)*

**위 표는 "이상적인 도형"의 수치이고, 정사면체의 실제 콜라이더는 이 도형이 아니다(§5.3).** 표의 값 자체는 유효하지만, 그 값을 **콜라이더에서 재서 얻으려 하면 안 된다.**

### 5.2 격자는 월드가 아니라 "진입 지점 상대"다

두 도형의 격자는 **원리적으로 정렬 불가능하다.** 스텝 비율이 1.0 : 0.8165 = √(3/2)로 **무리수**라 어떤 정수배에서도 격자점이 겹치지 않고, 방향도 4 vs 6이다.

따라서 월드 격자에 스냅하지 않고 **`진입 지점 + N × 스텝`** 에 스냅한다. 각 도형이 자기 원점을 들고 다닌다.

**격자 원점을 다시 잡는 시점:**
1. 굴리기 모드 진입 시
2. 공중에 떴다가 착지한 직후 (§7.3)
3. 크기가 바뀐 직후 (§6.3)

### 5.3 셀 크기는 어디서 오는가 — 인스펙터도, 콜라이더 bounds도 아니다

디자이너가 입력할 수 있게 하면 **모서리 길이와 어긋난 값을 넣을 수 있고, 어긋나면 매 칸 오차가 누적되어 격자가 조용히 틀어진다.** 씬에서는 "몇 칸 굴리니까 벽에 낀다" 정도로만 보여 원인을 찾기 어렵다. 그래서 인스펙터에는 **읽기 전용으로 표시만** 한다. `DestructionSystem`이 축별 분할 수를 노출하지 않고 비율에서 자동 계산한 것과 같은 판단이다 — 디자이너가 손으로 맞춰야 하는 값은 반드시 어긋난다.

> ⚠️ **[2026-08-19 정정] "콜라이더 bounds에서 자동 계산"은 정사면체에서 틀린다.**
>
> 정사면체의 솔리드 콜라이더는 뾰족한 정사면체가 아니라 **꼭짓점을 이웃 쪽으로 15% 깎은 convex MeshCollider**다(`PlayerObjectMenuItem.cs:272-274` → `TetrahedronMeshGenerator.CreateChamferedColliderMesh(0.5f, 0.15f)`). PhysX 접촉 안정성을 위해 일부러 그렇게 만든 것이다.
>
> | | 이상적 정사면체 | 실제 콜라이더(깎인 것) |
> |---|---|---|
> | bounds 크기 | 1.3660 × 1.1547 × 1.3660 | **1.1928 × 0.9815 × 1.1928** |
>
> bounds로 모서리 길이를 역산하면 1.4142가 아니라 ~1.20이 나오고, 한 칸이 0.8165 대신 **~0.69**가 된다. **바로 이 절이 경고한 "매 칸 오차가 누적되어 조용히 틀어지는 격자"를, 이 절의 해법이 그대로 만들어낸다.** 게다가 이상적 정사면체조차 bounds(1.366) ≠ 모서리(1.4142)라 어떤 경우에도 변환계수 없이는 못 뽑는다. 정육면체는 `BoxCollider.size = (1,1,1)`이라 우연히 맞을 뿐이다.
>
> **확정: 셀 크기는 `Kind`별 기하 상수 × `transform.localScale.x`로 구한다.**
>
> | Kind | 모서리 길이(스케일 1 기준) | 한 칸 이동거리 |
> |---|---|---|
> | Cube | 1.0 | 1.0 × scale |
> | Tetrahedron | 1.4142 (= √2) | 0.8165 × scale (= √⅔) |
>
> 스케일이 균일 1:1:1로만 변하므로(§4.1 정정) `localScale.x` 하나로 충분하다. `TetrahedronMeshGenerator`에서 계산해 오는 방법은 **없다 — 그 파일은 `Editor/` 폴더에 있어 런타임 어셈블리에서 참조할 수 없다.** 상수를 쓰되 그 출처(정육면체에 내접하는 정사면체 → 모서리 = √2 × 반경 2)를 주석에 남긴다.
>
> **텀블 수학 자체는 깎여도 무사하다.** chamfer는 꼭짓점만 자르므로 **피벗이 되는 모서리 직선의 위치는 원본과 완전히 동일**하다(잘린 두 점이 원래 모서리 위에 그대로 남는다). §6의 피벗 고정 회전은 그대로 유효하고, 깎인 부분은 오히려 접지 불연속을 줄인다.

## 6. 텀블 중 크기 변경 안전성 ★

**`ScalingSystem`으로 크기가 바뀌면 셀 크기(= 모서리 길이)가 통째로 바뀐다.** 이는 부작용이 아니라 의도된 기믹 재료다(§9.4). 문제는 **크기가 텀블이 도는 도중에 바뀔 때**다.

### 6.1 왜 위험했나

- `PlayerShapeController`는 스케일을 즉시가 아니라 `Vector3.Lerp`로 **여러 프레임에 걸쳐** 바꾼다(`lerpSpeed`). 텀블 한 번이 0.29초인데 그 사이 내내 기하가 변한다.
- 텀블 중엔 `isKinematic`이라 **물리가 밀어내 주지 않는다.** 피벗 축과 몸 크기가 어긋나면 바닥을 그냥 파고들거나 공중에 뜬 채로 회전이 끝난다.

### 6.2 해법 — 피벗 고정 + 반경 매 스텝 재측정

**회전 중심을 무게중심이 아니라 접촉 모서리로 잡고, 그 피벗선을 월드에 고정한 뒤, 피벗→무게중심 벡터를 매 스텝 현재 크기로 다시 잰다.**

```
매 FixedUpdate:
    θ = 텀블각 × ease(경과 / 소요시간)
    r = (현재 스케일 기준) 피벗선 → 무게중심 벡터    ← 매 스텝 재측정
    자세 = 피벗 + Rot(피벗축, θ) · r
```

피벗선은 바닥 위에 고정돼 있고 접촉 모서리가 거기에 붙박여 있으므로, 몸은 커지든 작아지든 **위·뒤로만 자라고 절대 바닥을 향해 자라지 않는다.**

**검증(수치 시뮬레이션):**

| 시작 → 종료 모서리 | 수평 이동 | (시작+종료)/2 | 최저점(바닥 침투) |
|---|---|---|---|
| 1.0 → 1.0 | 1.0000 | 1.0000 | 0.00e+00 |
| 1.0 → 2.0 | 1.5000 | 1.5000 | 0.00e+00 |
| 1.0 → 0.5 | 0.7500 | 0.7500 | 0.00e+00 |
| 2.0 → 1.0 | 1.5000 | 1.5000 | 0.00e+00 |

**바닥 침투·부양이 어떤 경우에도 정확히 0이다.** 크기 변경 안전성이 런타임 보정이 아니라 **기하학적으로 보장**된다.

> **무게중심 기준으로 회전시키면 안 된다.** 그러면 크기가 변할 때 접촉점이 떠오르거나 파고든다. 회전축이 접촉 모서리라는 점이 이 안전성의 전부다.

> ⚠️ **[2026-08-19 추가] Root 원점은 무게중심이 아니다 — 이 절의 "무게중심"을 `transform.position`으로 읽으면 안 된다.**
>
> `PlayerShapeController`가 **매 FixedUpdate** 자식들의 로컬 위치를 강제한다: `Player_Mesh.localPosition.y = 0.5`(`Playershapecontroller.cs:200-210`), `Player_Collider.localPosition = (x, 0.5, z)` + `localScale = (1,1,1)`(`:139-148`). 즉 Root는 몸의 중심이 아니라 **대략 바닥에 놓인 기준점**이고, 도형마다 관계가 다르다 — 정육면체는 바닥면이 Root와 일치하지만 **정사면체는 바닥면이 Root보다 0.2113 U 위**에 있다(메쉬 무게중심이 원점이고 밑면이 로컬 −0.2887, 거기에 +0.5 오프셋).
>
> **따라서 피벗선과 무게중심은 `PlayerShapeIdentity.solidCollider`의 월드 기하에서 구하고, 실제로 움직이는 것은 Root다.** "Root 원점 = 접지점" 같은 상수 오프셋을 가정하면 정사면체에서 0.21 U 떠서 굴러간다.
>
> 이 강제 대입은 텀블 중에도 계속 돈다. 우리가 Root만 움직이는 한 충돌하지 않지만(우리는 자식 로컬 트랜스폼을 건드리지 않는다), **자식 트랜스폼으로 자세를 만들려는 구현은 매 스텝 덮어써진다.** 회전은 반드시 Root에 건다.
>
> 텀블 중에는 `isKinematic`이므로 자세 대입은 `rb.MovePosition`/`rb.MoveRotation`을 쓴다(보간이 살아 시각적으로 매끄럽다). `transform`에 직접 쓰면 물리 보간이 끊긴다.
>
> **씬에 저장된 값을 믿지 마라.** 씬의 `Player_Mesh`/`Player_Collider`는 셋 다 `localPosition (0,0,0)`으로 저장돼 있지만, `PlayerShapeController`가 첫 `FixedUpdate`에 y를 0.5로 **덮어쓴다**(세 플레이어 모두 `meshTransform`/`colliderTransform`이 연결돼 있음을 씬에서 확인). 즉 저장값과 런타임값이 다르다. 기하는 반드시 **런타임에 `solidCollider`의 월드 bounds/자세에서** 재고, 씬 인스펙터에 보이는 숫자로 계산하지 않는다.

### 6.3 귀결 — 이동거리 = (시작 + 종료) / 2

텀블 시작 시 무게중심은 피벗에서 `시작 반높이`만큼 뒤에, 종료 시 `종료 반높이`만큼 앞에 있다. 따라서:

> **한 칸 이동거리 = (시작 모서리 길이 + 종료 모서리 길이) / 2**

크기가 안 바뀌면 그냥 모서리 길이가 되어 §5.1과 정확히 일치한다. 크기가 바뀌면 그 텀블 한 칸만 중간값이 되고, **착지 지점을 새 격자 원점으로 다시 잡으므로**(§5.2) 이후 격자는 새 크기의 피치로 깨끗하게 이어진다.

### 6.4 남는 위험은 기하가 아니라 충돌 — 3단 정책

기하는 위 방식으로 안전해졌지만, **몸이 커지면 벽·천장에 새로 닿을 수 있다.** kinematic이라 물리가 밀어내지 않으므로 명시적으로 다룬다.

매 스텝 투영 자세로 겹침 검사를 하고, 막히면:

| 단계 | 상황 | 처리 |
|---|---|---|
| 1 | 정상 | 텀블 완료 → 착지 셀 스냅 |
| 2 | 도중 막힘 | **되감기** — θ를 역재생해 출발 셀로 복귀 |
| 3 | 되감기도 막힘 | dynamic 복귀 + 물리에 맡김 + **그 자리를 새 격자 원점으로** |

텀블이 θ의 순수 함수라 되감기가 공짜다(별도 상태 불필요). 3단계는 "커지느라 출발 셀조차 더 이상 안 들어가는" 극단 상황의 탈출구이며, 상대 격자라 재정렬 비용이 없다.

> **[2026-08-19 정정] 2단계 되감기는 "크기가 커진 극단 상황"이 아니라 평상시 막힘의 기본 반응이다.**
>
> 1차 구현은 `BeginTumble` 사전 검사에서 **도착 자세까지** 보고 막혀 있으면 아예 시작하지 않았다. 그러면 벽이든 절벽이든 도착 칸이 막힌 경우든 전부 같은 무반응이라 플레이어가 원인을 구분하지 못한다. 사전 검사에서 **도착 자세 검사를 빼** 셋으로 갈랐다: 호 중간부터 막힘(벽에 딱 붙음)·스냅 실패 → 제자리 무반응 / 도착만 막힘 → 텀블이 시작되고 이 표의 2단계 되감기가 돌아 **"굴러가다 튕겨 돌아오는"** 반응 / 절벽 → 그냥 굴러가서 떨어진다. 새 상태를 만들지 않고 이미 있는 되감기를 재사용한 것이 요점이다.

**[2026-08-19 추가] 겹침 검사는 어떤 API로 하는가 — 원문이 정하지 않았다.**

정사면체의 솔리드 콜라이더는 convex `MeshCollider`이고(§5.3) Unity에는 `Physics.OverlapMesh` 같은 것이 없다. 바운딩 박스로만 검사하면 정사면체가 실제로는 안 닿는데 막혔다고 판정해(§9.2의 정사면체 전용 터널이 통째로 막힌다) 이 기믹의 레벨 디자인 도구가 죽는다.

**확정: `Physics.ComputePenetration`을 쓴다.**

```

   (자기 자신의 콜라이더와 트리거는 제외)
2) 정밀 — 후보마다 Physics.ComputePenetration(
              solidCollider, 투영 위치, 투영 회전,     ← 몸을 실제로 옮기지 않고 "그 자세라면"
              후보, 후보.transform.position, .rotation,

   dist > 허용 오차면 막힘.
```

`ComputePenetration`이 이 목적에 맞는 이유는 **콜라이더를 실제로 그 자세로 옮기지 않고도 임의의 위치·회전을 인자로 받는다**는 점이다. kinematic 바디를 투영 자세로 옮겨보고 되돌리는 방식은 그 사이 한 스텝의 트리거·충돌 콜백이 새어 나간다(포탈 자신을 다시 밟는 것을 포함해). convex `MeshCollider`도 정식 지원된다.

### 6.5 교차 폴더 의존이 사라졌다

초기 검토에서는 `ScalingSystem/Playershapecontroller.cs`에 스케일 변경 큐를 넣어야 할 것으로 봤고, 그렇다면 **교차 폴더 하드 룰**에 걸려 사전 허가가 필요했다.

**피벗 고정 방식은 `transform.localScale`을 매 스텝 읽기만 하므로 그 의존이 통째로 없어진다.** `ScalingSystem`은 한 줄도 건드리지 않는다.

**[2026-08-19] 리시버를 `PortalSystem/`으로 옮기면서(§8.2) 교차 폴더 수정이 0이 됐다.** 두 파일(`Portal.cs`, `PlayerRollModeReceiver.cs`) 모두 `Assets/PortalSystem/` 안에 있고, `PlayerMover.ExternallyDriven` · `PlayerJump.enabled` · `PlayerVisualRoll.enabled` · `PlayerAccelReceiver.CancelBoost()` · `PlayerShapeIdentity.Kind`는 전부 **바깥에서 public 멤버를 읽고 쓰는 것**이지 그 파일을 고치는 게 아니다. 리시버도 포탈이 런타임에 붙이므로 `PlayerObjectMenuItem.cs`와 씬도 무수정이다. **하드 룰에 걸리는 사전 허가 항목이 하나도 남지 않았다.**

## 7. 상태 기계 — 진입과 이탈

### 7.1 포탈 한 쌍

입구 포탈 통과 → 굴리기 모드 진입. 출구 포탈 통과 → 해제. 포탈 컴포넌트에 **켬 / 끔 / 토글** 노브를 두어 레벨에서 편도 실험도 가능하게 한다(기본 토글).

**편도(맵 끝까지 유지)를 기본으로 두지 않는 이유:** 모드가 맵 나머지 전체로 새어 나가면 "구간을 예외로 선언"이 아니라 "그 이후 전부를 예외로 선언"이 되어, 선택 경로라는 전제가 무너진다.

### 7.2 Tab 전환 · 리스폰 · 낙사

| 사건 | 모드 | 왜 |
|---|---|---|
| **Tab 전환** | **유지** | 모드는 조작권이 아니라 그 *몸에 붙은 상태*다. 풀면 돌아왔을 때 격자에서 벗어난 위치에 서 있게 된다 |
| **리스폰(R)·낙사** | **해제** | 체크포인트가 굴리기 구역 밖일 수 있다. 거기서 굴리기로 부활하면 LD-01 필수 경로를 굴리기로 지나가게 된다 |

**Tab으로 조작권을 잃는 순간 진행 중인 텀블은 끝까지 완주시킨다.** 중간에 멈추면 모서리로 선 채 kinematic으로 굳는다. `ExternallyDriven` 중에는 `PlayerMover.FixedUpdate`가 최상단에서 return하므로 `DampWhenUncontrolled`가 텀블을 짓밟지 않는다(이미 안전).

**리스폰 감지 방법:** `RespawnController`에는 이벤트/훅이 없고 `RespawnPlayer(GameObject)` 단일 진입점뿐이다. **거기에 콜백을 다는 건 교차 폴더 수정이므로 하지 않는다.** 대신 리시버가 *"텀블 중이 아닌데 남이 이 몸을 붙잡았다"* 를 스스로 감지해 모드를 취소한다.

> ⚠️ **[2026-08-19 정정] 원문은 `isKinematic`만 보게 돼 있었는데, 그러면 리스폰의 절반을 놓친다.**
>
> `RespawnRoutine`은 **페이드 경로에서만** `isKinematic`을 켠다(`RespawnController.cs:374-378`). **킬 라인 리스폰은 `useFade: false`(낙하 연출)라 `isKinematic`을 아예 켜지 않고 `ExternallyDriven`만 켠다**(`:304`). 즉 `isKinematic`만 보면 *가장 흔한 리스폰인 장외 추락*을 통째로 못 잡는다.
>
> **판정은 반드시 `mover.ExternallyDriven || rb.isKinematic` 둘 다 본다** — `Assets/CLAUDE.md`가 "소유 신호가 하나가 아니다"로 명시한 그 관용구이고, `RespawnController.IsHeld`(`:352-356`)가 쓰는 식과 동일하다. 원문은 이 관용구를 인용하면서 절반만 적용했다.
>
> 우리 자신이 텀블 중 `ExternallyDriven`과 `isKinematic`을 **둘 다** 세우므로, 판정은 *"내 텀블 상태가 아닌데 저 둘 중 하나가 켜져 있으면 남의 소유"* 가 된다.

**[2026-08-19 추가] 반대 방향도 알아둬야 한다 — 텀블 중에는 리스폰이 아예 안 걸린다.**

`RespawnController.IsHeld`가 `ExternallyDriven || isKinematic`으로 "붙잡힘"을 판정하므로, 텀블이 도는 동안 우리 몸은 **붙잡힌 것으로 보인다.** 그 결과:

| 발동 | 텀블 중 동작 | 근거 |
|---|---|---|
| 수동 `R` · 외부 호출(낙석 피격) | **거절**(콘솔 로그 1줄) | `:336-341` |
| 킬 라인 · 장외 볼륨 | **연기** — 체류 타이머를 살려두고 풀리는 즉시 실행 | `:299` |

텀블 1회가 0.16~0.29초이고 텀블 사이 휴지기에는 두 플래그가 모두 내려가므로 실사용상 문제는 아니다. **다만 `홀드 반복 간격`을 0으로 두면 키를 누르고 있는 내내 휴지기가 거의 사라져 R이 먹지 않는 구간이 생긴다** — 플레이테스트에서 "굴리는 중엔 R이 안 먹는다"는 제보가 나오면 원인은 여기다. 필요하면 간격에 최소 하한(예: 0.05초)을 준다.

> **[2026-08-19 정정] "휴지기에 두 플래그가 내려간다"는 그대로지만, 그래서 그 휴지기에 `PlayerMover`가 기존 방식으로 몸을 미끄러뜨렸다(플레이테스트에서 확인).** 스냅 실패 · 막힌 칸 · 홀드 간격 · 공중 · 키를 누른 첫 프레임이 전부 그 구간이다.
>
> **해결을 `ExternallyDriven`을 모드 전체로 넓히는 쪽으로 하면 안 된다** — 위 표대로 `IsHeld`가 항상 true가 되어 킬 라인 리스폰이 무한 연기 = 소프트락이다. 대신 리시버를 `[DefaultExecutionOrder(200)]`으로 이동 관련 컴포넌트 중 맨 마지막에 돌리고, `!isKinematic`인 프레임마다 `rb.velocity`의 **수평 성분만** 0으로 만든다(Y는 중력·낙하의 소유물이라 절대 안 건드린다). 붙잡기 규칙은 이 표 그대로 남는다.
>
> 부작용으로 **공중에서도 수평 조작이 죽는다** — 확정 사양이다(굴리기 모드에서 수평 이동의 유일한 출처는 텀블).
>
> 한 가지 더: 놓는 조건은 "입력이 **아예 없을** 때"다. 입력은 있는데 스냅만 실패한 경우까지 놓으면 키를 누르고 있는 내내 `isKinematic`이 매 프레임 토글돼 Rigidbody 보간 이력이 리셋되고 눈에 띄게 튄다.

### 7.3 낭떠러지 — 그대로 낙하

목적지 셀에 바닥이 없어도 **텀블을 정상 완료하고 dynamic으로 복귀한다.** 그 뒤는 중력의 몫이다.

착지하면 **그 지점을 새 격자 원점으로 다시 잡는다.** 모드는 유지된다(굴리기 구간 안에서 한 단 아래로 떨어지는 것은 정상 이동이다).

**[2026-08-19 추가] 착지 판정은 `PlayerGroundContact.IsGrounded`를 그대로 쓴다 — 텀블 중에도 죽지 않는다.**

`PlayerGroundContact`는 두 신호를 OR로 합치는데, 그중 **아래 방향 SphereCast는 매 `FixedUpdate` 도는 물리 쿼리라 `isKinematic`과 무관하게 계속 동작한다**(`PlayerGroundContact.cs:57-68`). `OnCollisionStay` 쪽(`:75`)은 kinematic 바디에서 안 불릴 수 있지만, SphereCast가 그 구멍을 메우므로 접지·바닥 법선 모두 텀블 중에도 유효하다. 별도의 자체 접지 판정을 만들 필요가 없다.

**반면 `PlayerGravityOverride`는 텀블 중 얼어붙는다** — `rb.isKinematic`이면 즉시 return한다(`PlayerGravityOverride.cs:97-99`, kinematic 바디에 `AddForce`가 에러라서 그렇게 만들어 둔 것이다). 텀블 중에는 중력이 필요 없으니 무해하고, 텀블 사이 휴지기에는 dynamic이라 배율이 다시 걸린다. 무중력 버블 안에서 굴려도 정상이다 — 단 **"텀블 중에는 버블의 중력 배율이 적용되지 않는다"** 는 것을 알고 있어야 한다(굴리기가 무적 이동인 §9.5의 연장선이다).

### 7.4 홀드 연속 굴림

방향키를 누르고 있으면 `홀드 반복 간격`마다 다음 텀블을 시작한다.

**정사면체에서 이 규칙이 예쁘게 풀린다.** 홀드 중 매 텀블마다 "현재 유효한 3방향 중 입력에 가장 가까운 것"으로 다시 스냅하면, W를 누르고 있는 것만으로 45° → 105° → 45° … 지그재그가 자동으로 나온다. **별도 코드 없이 §4.2의 규칙에서 그냥 떨어지는 동작**이고, 정사면체의 정체성이 된다.

정육면체는 4방향이 항상 유효하므로 홀드하면 그대로 직진한다.

### 8.2 `Assets/PortalSystem/PlayerRollModeReceiver.cs` (수신자)

> ⚠️ **[2026-08-19 정정] 원문은 이 파일을 `Assets/PlayerSystem/`에 두게 돼 있었다. 컨벤션 위반이다.**
>
> 이 저장소의 리시버는 **전부 자기 기믹 폴더에 산다** — `AccelSystem/PlayerAccelReceiver.cs`, `WindZoneSystem/PlayerWindReceiver.cs`. `Assets/CLAUDE.md`의 *"새 기믹을 추가할 때는 반드시 새 폴더를 만든다. 기존 기믹 폴더 안에 다른 기믹의 스크립트를 섞어 넣지 않는다"* 와 **교차 폴더 하드 룰**에 모두 걸린다. 이름이 `Player~`로 시작한다고 `PlayerSystem/`에 두는 게 아니다.
>
> `PortalSystem/`에 두면 **`PlayerSystem`을 포함해 다른 폴더의 파일을 한 줄도 고치지 않는다**(§6.5). `ExternallyDriven` 설정, `PlayerJump.enabled` 토글 등은 전부 **바깥에서 public 멤버를 읽고 쓰는 것**이지 그 파일을 수정하는 게 아니다.

### 8.3 같이 처리해야 하는 것 (빼먹으면 버그)

| 대상 | 처리 | 안 하면 |
|---|---|---|
| `PlayerMover.ExternallyDriven` | 텀블 중 `true` | 이동 대입이 텀블을 짓밟는다 |
| `PlayerMover.enabled` | **절대 건드리지 않는다** | `PlayerControlSwitcher` 로스터에서 빠져 Tab 순환이 깨진다(실타래 Phase 1에서 이미 치른 부채) |
| `PlayerAccelReceiver` | 모드 진입 시 **`CancelBoost()`** | `ExternallyDriven`을 안 보고 매 FixedUpdate velocity를 통째 대입해 그대로 뚫린다 |
| `PlayerVisualRoll` | 모드 중 비활성 + 이탈 시 `localRotation` identity **및 `localPosition` 복원** | 시각 메쉬가 실제 피벗 회전을 거슬러 계속 기울인다(이중 적용) |
| `PlayerJump` | 모드 중 `enabled = false`, 이탈 시 복원 | 텀블 사이 휴지기(dynamic + 접지)에 Space가 정상 발사되어 격자 정렬이 깨진다 |
| Root 회전 | 텀블 완료 시 정준 자세로 스냅 | `ScalingSystem`의 X/Y 독립 스케일 축이 뒤바뀐다 |

> ⚠️ **[2026-08-19 정정] `PlayerVisualRoll`은 회전만 쓰지 않는다.** 매 프레임 `visual.localPosition = baseLocalPosition - sinkNormal * sinkAmount`로 **위치도 쓴다**(`PlayerVisualRoll.cs:143`, 비탈에서 메쉬가 뜨는 걸 막는 침하 보정). 회전만 identity로 되돌리고 비활성화하면 **가라앉은 위치가 그대로 굳어** 모드 내내 메쉬가 바닥에 박힌 채 굴러간다. `localRotation`과 `localPosition`을 **둘 다** 복원한다(위치는 `baseLocalPosition`으로). 이 대상은 손자 `Player_MeshVisual`이라 `PlayerShapeController`가 강제하는 `Player_Mesh`와는 다른 트랜스폼이다 — 서로 안 부딪힌다.

> ⚠️ **`PlayerJump`에 게이트를 추가하지 마라.** `Assets/CLAUDE.md`에 *"`PlayerJump`는 `ExternallyDriven`을 안 보지만 고칠 필요가 없다 … 다시 시도하지 마라"* 가 명시돼 있다. 컴포넌트를 끄는 방식으로 처리한다 — `PlayerJump`에는 `OnEnable`/`OnDisable`이 없어 로스터 부작용이 없다(`PlayerMover`와 다르다).

## 9. 기하학적 제약 = 레벨 디자인 도구 ★

이 기믹의 제약들은 우회 대상이 아니라 **그대로 레벨 디자인 도구다.** 태그 판별도, 무게 게이트도, 표지판도 없이 기하학이 통행 규칙을 만든다.

### 9.1 복도 폭 게이트 — 정육면체 전용 통로

정사면체는 직진이 불가능해 좌우로 **0.408 U** 흔들리며 나아간다. 몸통까지 합치면:

| | 필요 복도 폭 |
|---|---|
| 정육면체 (직진) | **1.00 U** |
| 정사면체 (외접 자세 기준, 안전) | **2.04 U** |
| 정사면체 (내접 자세 기준, 빡빡) | 1.22 U |

> **폭 1.0 ~ 1.2 U 복도 = 정육면체 전용 통로.** 세모는 물리적으로 못 들어간다.

### 9.2 천장 게이트 — 정사면체 전용 터널

텀블 중 최고점은 정육면체 1.414 U / 정사면체 1.225 U다.

> **높이 1.25 ~ 1.40 U 터널 = 정사면체 전용.**
> 네모는 *굴러서는* 못 들어간다. **걸어서는 들어간다** — 굴리기 모드에서만 막히는 층위가 하나 더 생긴다.

⚠️ **역으로, 굴리기를 시킬 구간의 천장 여유는 1.42 U 이상이어야 한다.** "몸이 1.0 U니까 1.1 U 터널이면 되겠지"로 깔면 굴리기가 물리적으로 불가능한 구간이 되고, 증상은 "왜 안 굴러가지?"로만 보인다.

### 9.3 6방향 제약 — 세모는 월드 축으로 못 간다

정사면체의 순 진행 방향은 15° / 75° / 135° / 195° / 255° / 315°다. **월드 축(0°/90°/180°/270°)이 하나도 없다.** 축 정렬 격자로 지은 맵에서 세모는 대각으로만 흐르므로, 같은 바닥 위에서도 두 도형의 도달 가능 영역이 자연히 갈라진다.

### 9.4 크기 변경 = 격자 자체를 바꾸는 열쇠

굴리기 구간 **진입 전** 또는 **구간 안**에서 `ScalingSystem`으로 크기를 바꾸면 셀 크기가 통째로 바뀐다(§6에서 텀블 중 변경까지 안전하게 만들었다).

| 스케일 | 셀 크기 | 천장 소요 |
|---|---|---|
| 0.5배 | 0.50 U | 0.707 U |
| 1.0배 | 1.00 U | 1.414 U |
| 1.5배 | 1.50 U | 2.121 U |
| 2.0배 | 2.00 U | 2.828 U |

- **작게** → 잘게 굴러 좁은 틈·낮은 천장을 통과. 대신 한 칸이 짧아 넓은 틈을 못 건넌다.
- **크게** → 한 칸이 2.0 U라 큰 틈을 한 번에 넘지만, 천장 2.83 U가 필요해 대부분의 통로에 못 들어간다.
- **격자 피치가 달라지므로 "특정 크기에서만 딱 맞는 발판 배치"** 가 가능하다 — 2.0 U 간격 발판은 2배에서만, 0.5 U 간격 징검다리는 0.5배에서만 밟힌다. **열쇠 구멍 퍼즐이 기하학에서 그냥 나온다.**

### 9.5 굴리기 = 무적 이동

텀블 중 `isKinematic`이라 다른 물체가 이 몸을 밀 수 없다. 낙석이 맞아도 안 밀리고 그 위에 얹히지도 않는다.

> **낙석 커튼 아래를 굴러서 통과하는 구간이 성립한다.**
> 대신 그 상태로는 **벽을 깨거나 모래시계를 뒤집을 수 없다.**
> — *"굴러서 지나갈 수는 있지만 아무것도 부술 수 없다"* 가 명확한 규칙이 된다.

이로써 §10 C군의 `FallingRock` / `Destruction` / `FallingRockFlip` 3건은 "금지"가 아니라 **의도된 제약**으로 신분이 바뀐다.

### 9.6 계단형 낙차 게이트 — 재접지 보정 상한이 최대 단 높이다

**[2026-08-20 추가]** §7.3의 "낭떠러지 그대로 낙하"와 별개로, **단 높이가 얕은 계단은 낙하가 아니라
매 텀블의 재접지 보정으로 흡수돼야 매끈하다.** `PlayerRollModeReceiver.SnapPivotToGround`가 매
텀블 시작마다 피벗 Y를 실제 바닥에 다시 얹는데(§5.2 각주), 그 보정 폭에 상한
(`GroundSnapCorrectionCap = 0.25 × scale`)이 있다 — 절벽·계단 턱에 걸치면 히트가 아래층 바닥이라
보정하면 몸이 한 층 순간이동하기 때문이다(코드 주석 참고).

**이 상한을 넘는 단 높이의 계단은 "얕은 계단"이 아니라 "매 단이 작은 절벽"으로 취급된다.**
2026-08-20 플레이테스트에서 단 높이 0.35 U(상한 0.25보다 큼)로 만든 테스트 계단을 내려가자
"텀블 → 짧게 뜸 → 낙하 → 재접지"가 매 단 반복되는 스타카토 동작이 보고됐고, 그 낙하-재접지 반복이
누적돼 결국 `fallExitGrace`(§7.2 유예)를 넘겨 모드가 풀리는 경우까지 나왔다. **원인은 처음 의심했던
`fallExitGrace` 여유 부족이 아니라 재접지 보정 자체가 개입하지 않은 것**이었다(전문가 검토로 확인,
`PortalSystem/CLAUDE.md` 참고).

> **확정: 계단형 낙차(단 높이) ≤ `0.25 × scale`.** 이 이하면 매 텀블이 재접지로 매끈하게 흡수해
> 뜸도, 어색함도 없다. 이보다 큰 낙차가 필요한 지형은 §7.3의 "낭떠러지"로 설계하거나(모드 유지/해제
> 여부는 `exitRollModeOnFall`·`fallExitGrace`가 결정) 계단 자체를 굴리기 구간 밖에 둔다. 경사면과
> 마찬가지로 **텀블 모델을 계단 전용으로 재설계하는 것은 범위 밖**이다.

## 11. 레벨 설계 계약 — LD-01과의 관계

**규격표도, LD-01도, "네모 단독 완주 테스트 통과" 머지 조건도 한 글자도 고치지 않는다.**

`PlayerSystem_Requirement.md` #8에 이미 이 조항이 있다:

> **[예외] 지름길, 숨겨진 길, 보상 경로만 특정 도형 전용 규격 허용**

굴리기 구간을 선택 경로로 두면 이 조항에 그대로 해당한다.

⚠️ **필수 경로에 두면 즉시 깨진다.** 굴리기는 정육면체·정사면체 전용인데, 하필 네모가 LD-01 완주 주체다. 필수 경로에 굴리기 구간이 있으면 네모 완주 테스트가 그 구간을 반드시 통과해야 하므로 머지 조건이 무너진다. **"도형 전용"과 "선택 경로"는 세트여야 한다.**

## 12. 확정값 / 기본값

| 항목 | 값 | 근거 |
|---|---|---|
| 텀블각 (정육면체 / 정사면체) | 90° / 109.47° | 기하 고정, 노출 안 함 |
| 셀 크기 | 자동 도출 | §5.3 — 읽기 전용 표시만 |
| 텀블 1회 소요 시간 (정육면체) | **0.286 s** | 1.0 U ÷ 이속 3.5 — 걷는 속도와 연결 |
| 텀블 1회 소요 시간 (정사면체) | **0.163 s** | 0.8165 U ÷ 이속 5.0 (지그재그라 순 진행 4.33 U/s) |
| 홀드 반복 간격 | ~~0.05 s~~ → **0.03 s** | 0이면 리스폰이 안 걸리는 구간이 생긴다(§7.2). 아래 정정 참고 |
| 입력 스냅 허용 각도 | 30° (정사면체 기준 방향 간격의 절반) | 경계에서 애매하면 아무것도 안 함 |
| 포탈 모드 | 토글 | §7.1 |
| 절벽에서 모드 해제 | 켬 (`exitRollModeOnFall`) | 아래 정정 참고 |

**인스펙터에 노출하는 것은 3개뿐이다:** 텀블 소요 시간 / 홀드 반복 간격 / 입력 스냅 허용 각도.

> **[2026-08-19 정정 3건]**
>
> 1. **노브는 리시버가 아니라 `Portal`에 있다.** 리시버는 포탈이 런타임에 `AddComponent`하므로 씬에 존재하지 않는다 = 리시버 쪽 public 필드는 **아무도 인스펙터에서 조정할 수 없다.** 같은 값을 `Portal`에 두고 리시버를 얻는 즉시 복사한다. 값이 다른 문을 여럿 지나면 마지막 문이 이긴다.
> 2. **홀드 반복 간격 0.05 → 0.03**, 그리고 이징 곡선을 `Mathf.SmoothStep`(ease-in-out)에서 **ease-in `1 − cos(t·π/2)`** 로 바꿨다(§14의 미정 항목 해소). SmoothStep은 매 칸 끝에서 속도가 0으로 죽었다가 다시 0에서 출발해 홀드 간격과 겹치면 "죽은 시간"이 두 배가 되고, 그게 연속 회전의 버벅임이었다. **칸 리듬 자체는 유지한다** — 완전 연속으로 만들지 않는다(확정).
> 3. **`exitRollModeOnFall` 노브가 추가됐다.** 켜면 발밑이 빌 때 굴리기가 풀려 기존 이동 방식으로 돌아가고(리스폰 깃발이 없는 구간용), 끄면 모드를 유지한 채 몸만 놓아 수직 낙하한다(포탈 뒤에 깃발을 둔 맵용). 둘 다 `IsHeld`가 false라 킬 라인·R 리스폰은 정상 작동한다.
