# 태엽 축 (Windup Axle) — PRD

> 독립 신규 기믹. 사용자가 사전 작성한 상세 설계 초안(`태엽축_구현사항.md`, 저장소 루트)을
> 저장소 PRD 형식으로 옮기고, 초안 12번 "미확정 사항" 중 사용자와 상의해 확정한 항목을 반영한다.
> 원 설계 내용(상태 모델·의사코드·수치)은 이 문서에서 변경하지 않았다 — 형식만 갖췄다.
> 상태: **1차 구현 완료(코어 + `IWindupReceiver` + 회전판 + 패들 입력), 씬 배치·플레이테스트 전.**

## 1. 기획 의도 / 목적

태엽 축은 "누르면 즉시 반응하는" 발판·문·레버 계열과 달리, **에너지를 저장했다가 시간에
걸쳐 스스로 풀어내는 축적기(Accumulator)**다. 플레이어가 손을 뗀 뒤에도 저장량이 남아있는
동안은 계속 장치를 구동한다는 점이 이 기믹의 핵심이고, 다른 기믹과 구분되는 지점이다.

- 다른 기믹(AccelPad 등)은 "지금 상호작용 중인가"가 곧 출력이지만, 태엽 축은 "과거에 얼마나
  감아뒀는가"가 출력을 결정한다 — 입력과 출력이 시간적으로 분리된다.
- "조금 감았을 때"와 "최대로 감았을 때"의 결과가 달라야 하고, 방향(정/역)을 반대로 감으면
  연결 장치도 반대로 움직여야 한다는 것이 기획 요구의 핵심이다(초안 1번 원본 요구사항 참고).
- 태엽 축 자신은 **무엇에 연결되어 있는지 모른다.** 레일카·회전판·회전 계단처럼 서로 다른
  장치에 재사용 가능해야 하므로, 축은 "충전 상태를 신호로 내보내는 것"까지만 책임지고 그
  신호를 어떻게 해석해 움직일지는 전적으로 수신 측(파생 장치)의 몫이다.

## 2. 동작 시나리오

플레이어가 축을 돌리면(구체적 조작 방식은 이 문서 범위 밖, §5 참고) 그 회전량이 부호 있는
저장량(`currentCharge`)에 누적된다 — 정방향(상승/전진)이면 양수 쪽으로, 역방향(하강/후진)이면
음수 쪽으로 쌓인다. 반대 방향으로 감으면 기존 충전량을 먼저 상쇄한 뒤에야 반대 부호로 쌓이므로,
실제 태엽을 반대로 감을 때 먼저 풀리는 느낌이 별도 분기 없이 자연히 성립한다.

플레이어가 손을 떼도(`isWinding == false`가 되어도) 저장량은 즉시 멈추지 않는다. 방전
(`dischargeRate`)이 계속 진행되며 저장량을 소모해 출력 신호를 만들어내고, 여기에 더해 자연
감쇠(`decayRate`)가 출력과 무관하게 저장량을 별도로 갉아먹는다. 두 소모는 동시에 같은 저장량을
0 쪽으로 수렴시키는 별개의 요인이다. 저장량이 완전히 0에 도달하면 더 깎을 것이 없으므로 자연
감쇠도 적용되지 않는다 — 별도 "정지 상태"를 만들지 않고 `currentCharge != 0` 조건 하나로
자연히 멈춘다.

출력 세기는 저장량 비율(`chargeRatio = |currentCharge| / maxCharge`)을 `dischargeCurve`에
태워 계산한다. 곡선을 선형으로 두면 "소진될 때까지 일정한 힘", 감속형으로 두면 "풀릴수록
약해지는" 태엽 특유의 느낌을 낼 수 있다 — 세기 자체를 곡선 하나로 조율 가능하게 열어둔다.

축은 매 틱 이 출력을 신호로 내보내는 것으로 자기 역할을 마친다. 신호를 받아 실제로 움직이는
레일카·회전판·회전 계단 등은 이 문서의 범위 밖이며, 씬을 나갔다가 다시 들어오면 `currentCharge`는
항상 0에서 다시 시작한다(별도 저장/복원 로직 없음).

## 3. 컴포넌트 / 스크립트 설계

저장소 공통 발신자-수신자 분리 패턴(`Assets/CLAUDE.md`)을 따르되, 이 기믹은 그 패턴의 일반적
형태와 다른 지점이 있다 — 보통의 발신자(예: `AccelPad`)는 `GetComponentInParent<T>()`로
**특정한 수신자 타입**을 찾아 그 수신자의 public 메서드를 직접 호출하지만, 태엽 축은 자신에게
연결된 대상이 레일카인지 회전판인지 회전 계단인지 전혀 모른 채 신호만 발신한다. 즉 발신자는
하나(`WindupAxle`)로 고정되지만 **수신자 타입은 미확정이며 여러 종류가 될 수 있다** — 이 점이
"장치가 바뀌어도 축을 재사용할 수 있어야 한다"는 완료 조건의 근거이기도 하다.

- **`WindupAxle`** (가칭, 발신자·상태 보유자 하나) — 초안 3~10번의 상태 모델·입력 경계
  (`ApplyRotation(float signedDelta)`)·충전/방전/자연 감쇠 로직·출력 세기 계산을 그대로 갖는
  단일 컴포넌트. 축 자신의 시각 피드백(발광·인디케이터 회전, 초안 9번)도 이 컴포넌트가 직접
  처리한다 — 자신의 표현이므로 별도 발신 대상이 필요 없다.
- 실제 입력을 감지해 `ApplyRotation`을 호출하는 스크립트, 그리고 신호를 구독해 움직이는
  파생 장치 스크립트는 이 PRD의 범위 밖이다(§5).

## 4. 확정값 / 기본값

| 파라미터 | 타입 | 설명 | 상태 |
|---|---|---|---|
| `maxCharge` | `float` | 저장량 최대치 | 씬 튜닝 대상 |
| `chargeRate` | `float` | 입력 델타 대비 충전 속도 | 씬 튜닝 대상 |
| `dischargeRate` | `float` | 초당 유효 방전(출력)량 | 씬 튜닝 대상 |
| `decayRate` | `float` | 초당 자연 손실량 | 씬 튜닝 대상 |
| `dischargeCurve` | `AnimationCurve` | 충전 비율 → 출력 배율 매핑 | 씬 튜닝 대상 |
| `directionDeadzone` | `float` | 방향 판정을 위한 최소 입력 임계값 | 씬 튜닝 대상 |

아래는 파라미터가 아니라 동작 규칙으로서 확정된 사항이다.

| 항목 | 확정 내용 |
|---|---|
| 오버차지 처리 | `Mathf.Clamp(currentCharge, -maxCharge, maxCharge)` 단순 clamp만 적용한다. 반발(튕김) 피드백은 넣지 않는다(확정, 필요시 인디케이터로 최대치 도달을 전달) |
| 완전 방전 시 자연 감쇠 | `currentCharge == 0`이면 감쇠 대상 자체가 없으므로 적용되지 않는다 — 의도된 동작 |
| 영속성 | 씬 진입 시 `currentCharge`는 항상 0으로 초기화된다. 별도 저장/복원 로직 없음 |
| 정지 후 방전 지속 | `isWinding == false`가 되어도 방전(`dischargeRate`)은 계속 진행되고, 충전(`chargeRate`)만 멈춘다 — "충전-방전 축적기" 모델의 전제이므로 확정 |
| 입력 감지 방식 | 이 PRD 범위 밖. `ApplyRotation(float signedDelta)` 계약만 명시하며, 마우스/키/게임패드/XR 등 구체적 조작 방식은 후속 문서에서 다룬다 |
| 신호 발신 채널 | **병행**. 매 틱 도는 연속값(`outputPower`, `chargeRatio`)은 강타입 인터페이스(`IWindupReceiver.ApplyOutput(float power, float ratio)`)로, 완충/완전방전 같은 이산 이벤트는 저장소 기존 관례(`HourglassSystem`, `RespawnSystem` 등)를 따라 `UnityEvent`로 발신한다. 저장소에 다중 수신자 타입(레일카/회전판/회전계단)이 하나의 발신자에 붙는 첫 사례라 강타입 인터페이스를 새로 도입하되, 이산 이벤트는 기존 패턴을 그대로 재사용한다 |
| 다중 구독자 분배 | **전체 브로드캐스트**. 등록된 모든 구독자(`List<IWindupReceiver>`, `UnityEvent` 리스너 전부)가 매 틱 동일한 신호를 받는다. 우선순위/배타 구독 로직은 넣지 않는다 — 여러 파생 장치가 한 축에서 동시에 구동되는 상황이 기획 요구에 자연스럽다 |

## 6. 완료 조건 대비 검증

| 완료 조건 | 충족 방식 |
|---|---|
| 조금 감았을 때와 최대로 감았을 때 작동 결과가 다르다 | `outputPower = dischargeCurve.Evaluate(chargeRatio) * sign`로 세기가 `chargeRatio`에 비례 |
| 방향을 반대로 감으면 연결 장치도 반대로 작동한다 | `currentCharge`의 부호가 곧 `outputPower`의 부호를 결정 |
| 연결 대상이 바뀌어도 태엽 축을 재사용할 수 있다 | 축은 신호 계약만 발신하고 수신 측 해석에 관여하지 않음(원칙 수준에서 충족, 실제 발신 채널 구현은 §5에서 별도 확정) |
